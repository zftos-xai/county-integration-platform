# 规范采用与推广

## 分层模型

将规则分为团队底线、技术栈规则和项目覆盖项。推广时复制前两层，重新确认第三层。包名、端口、数据库版本、业务术语和法规结论通常属于项目覆盖项。

每条强制规则维护以下属性：

| 属性 | 含义 |
| --- | --- |
| 标识 | 稳定、可引用的规则编号 |
| 范围 | 哪些仓库、目录或变更适用 |
| 理由 | 要避免的具体故障或风险 |
| 门禁 | 自动命令或人工检查点 |
| 负责人 | 解释规则与批准例外的人 |
| 例外 | 申请字段、补偿措施和最长有效期 |

## 推广顺序

1. 盘点现状，不立即修改业务代码。
2. 确认技术栈和项目覆盖项。
3. 建立 `AGENTS.md`、Markdown 规范、`.editorconfig` 和统一验证入口。
4. 把现有可通过的检查先接入 CI。
5. 将存量缺口分批治理，区分新增代码门禁与历史债务。
6. 在一个真实变更中试点，验证误报、耗时和责任边界。
7. 启用受保护分支的必需检查并发布版本说明。

## 例外记录要求

例外记录至少包含规则编号、影响范围、业务原因、风险、补偿措施、负责人、批准人和到期日。到期未关闭的例外必须重新阻断。安全秘密、敏感数据泄露、虚假验证证据和未经授权的破坏性操作不能用普通例外放行。

## 版本与兼容性

- 主版本：改变现有项目的采用方式或新增破坏性门禁。
- 次版本：新增兼容规则、检查器或技术栈资料。
- 补丁版本：澄清描述、修复误报或文档错误。

插件升级前先在样板仓库和一个真实项目运行审计与验证。技能输出只能辅助决策；CI、评审所有权和分支保护才是执行机制。
