## 功能、安全和运行问题

### R01 / P1：依赖目录失败时仍删除旧关联

位置：`HospitalDirectorySyncServiceImpl.java:174`、`:280`、`:315`；`HospitalDirectorySyncMapper.xml:107`。

`validate` 通过 `relationTargetWasSynchronized` 跳过依赖失败的关系，随后 `synchronizeType` 无条件执行 `deleteRelationsForType`。例如科室失败、病区成功时，新病区—科室关系为空，但既有关系仍被删除；注释却承诺“不替换该关系”。本轮方法级反例已确认删除调用。

修复方向：主记录同步与关系快照替换分别判断完整性；只有依赖已成功且当前关系集合完整时才能替换。回归必须预置旧关系，断言依赖失败后关系仍保留，不能只验证没有调用失效标记。

### R02 / P1：HIS 超时没有覆盖响应正文读取

位置：`his/client/SoapPhisClient.java:213`—`:227`。

请求配置 timeout 后使用 `BodyHandlers.ofInputStream()`，再同步阻塞 `readNBytes`。响应头及时到达但正文停滞时，读取可超过配置期限，长时间占用请求线程及活动同步批次。16MB 大小上限不能替代时间上限。

修复方向：传输层统一约束从发送到完整收包的期限，保留流量上限，并确保超时会取消请求、关闭正文。补充慢响应头、慢正文、持续滴流、超大正文与中断测试，不给每个业务方法重复加超时判断。

### R03 / P1：数据库修复器把 MAX 缩短误判为扩容

位置：`framework/database/DatabaseContractRepairPlanner.java:33`—`:39`。

SQL 元数据用 `-1` 表示 MAX，代码直接比较整数，导致实际 MAX 到预期有限长度被批准，反方向的扩容却被拒绝。探针生成了允许执行的 `NVARCHAR(50)`。

修复方向：长度比较显式处理 MAX 的无界语义；同时确认实际和目标类型、可空性等未发生本次未批准的变化。补 MAX→有限、有限→MAX、Unicode 字节长度边界测试。事务能回滚执行错误，不代表错误 DDL 一定会失败，不能以“有事务”判定安全。

### R04 / P1：修复 DDL 遗失精度，复验又只看原差异码

位置：`DatabaseContractRepairPlanner.java:70`—`:77`；`DatabaseContractMaintenanceServiceImpl.java:226`—`:237`。

非字符类型直接返回类型名，未使用 `DatabaseContractColumn.precision/scale`。单纯放宽可空性，也可能顺带改变 decimal 或 datetime2 的类型参数。执行后仅判断原来的“差异码＋对象名”是否消失，新产生的同字段精度差异不会因此让 `passed` 变为 false。

修复方向：生成完整且不带额外改变的类型声明；不支持安全生成的类型明确拒绝。复验目标字段完整契约，并拒绝本次执行引入的新差异。必须在 SQL Server 2012 SP4 验证实际 DDL 和回滚，当前只有规划器级证据。

### R05 / P1：医疗目录错误明细可撑爆失败摘要字段

位置：`MedicalDirectoryValidationServiceImpl.java:52`—`:61`；`MedicalDirectorySyncServiceImpl.java:204`、`:236`；`V1000__medical_directory_sync_main.sql:81`。

冲突编码逐项加入 failures，最后直接 join；分项落库使用该字符串，目标列为 `NVARCHAR(500)`。批次总摘要虽另有截短，并未保护每个分项摘要。30 个简短冲突就输出 589 字符；更长来源编码会更早越界。由字段契约可判断最终写入不兼容，但本轮没有实库执行截断错误。

修复方向：生成失败结论时按错误类别、数量和有限样例构成有界摘要，不能先无限堆积再在多个 Service 各自截断。增加 500 字符边界、海量冲突及终结事务失败用例。

### R06 / P1：分项已提交、批次仍 FETCHING，没有中断恢复闭环

位置：`MasterDataBatchServiceImpl.java:99`—`:118`；两类 `*DirectorySyncServiceImpl.synchronize/finishRun`；`MasterDataBatchMapper.xml:211`；`V0600__master_data_main.sql:88`。

抢占批次单独提交；各类型数据单独提交；分项事实与批次终态到最后才集中保存。进程中断或最后一次保存失败，可能留下已修改的目录、缺失的分项结果和长期 FETCHING 批次。当前 run 只接收 CREATED/RESULT_UNKNOWN，cancel 只接收 CREATED，活动范围唯一索引继续阻止后续批次。

修复方向：每类目录变更与该类结果事实同事务持久化；为失去执行者的批次定义租约/执行标识及受控恢复规则。进程退出不是 finally 能完全覆盖的情况，不能只加总 catch。禁止自动把未知结果伪装为成功或直接无条件重试。

### R07 / P2：Controller 密码校验允许编码器不支持的输入

位置：`ChangePasswordRequest.java:14`、`CreateUserCommand.java:24`、`ResetPasswordRequest.java:11`、`BootstrapCommand.java:27`；`SecurityConfiguration.java:67`。

这些输入用 `@Size(max=128)` 限字符数，实际 BCrypt 限 UTF-8 72 字节。输入在 Web 边界通过后才在编码阶段抛异常，正是“基础校验滞后”的另一种形式。

修复方向：统一密码输入契约并在 Web 入口执行可复用字节约束；不要截断密码。若改变编码算法，须另做兼容迁移设计，不能在 Func 中悄悄预处理密码。使用真实 PasswordEncoder 测试 ASCII 与多字节边界，不能只 Mock 编码器。

### R08 / P1：改密的并发冲突检查没有对应 SQL 条件

位置：`IdentityServiceImpl.java:133`—`:145`；`IdentityMapper.xml:178`—`:193`。

先读旧哈希并验证，更新时仅判断 id 和 enabled。两个改密操作，或用户改密与管理员重置交错时，后写入者可覆盖刚刚更新的密码并清除强制改密标志。检查影响行数并抛“密码状态已变化”，无法检测仍启用用户的哈希变化。

修复方向：更新比较读取时的凭证版本/哈希，或对同一凭证状态执行一致的锁定协议。增加交错改密、重置竞争测试；事务注解本身不能代替比较条件。

### R09 / P2：普通改密后其他旧会话仍能继续使用

位置：`SessionController.java:150`—`:162`；`ActiveAccountFilter.java:50`—`:97`；`UserAccount.java`。

改密后只登出当前请求的 session；过滤器比较启用、机构与权限，不比较密码变化时间或凭证版本。其他已登录会话在权限未变时仍可访问。这是已确认的失效机制缺口，未在本轮启动完整应用做双会话攻击复现。

修复方向：明确改密/重置后的会话撤销策略，采用不可包含密码明文或哈希的凭证版本比较。普通改密、强制改密、管理员重置、其他浏览器旧会话均须覆盖。

### R10 / P2：缺少 enabled 的请求会被当成“停用”

位置：`ChangeEnabledRequest.java:11`、`ChangeOrganizationEnabledRequest.java:13` 及相应 Controller。

primitive boolean 不能区分未提供和 false。只有合法 version 的 JSON 被绑定为 false，Bean Validation 为零错误；符合其他条件时将执行停用。请求目标状态应由调用方明确给出，而不是反序列化默认产生。

修复方向：HTTP 输入使用 `@NotNull Boolean` 或明确的必填反序列化约束，校验后再向业务方法传 boolean。复核其他更新 DTO 的 primitive 必填字段，不在 Service 补“是否缺失”的判断。

### R11 / P1：所谓安全摘要只是截短，未隔离不可信错误内容

位置：两类 `*DirectorySyncServiceImpl.safeFailure/technicalFailure`；`MedicalDirectoryFetchServiceImpl.safeError`；`SoapPhisClient.redactCredential`。

来源错误大多只替换换行并截短；SOAP 客户端只移除当前授权码的精确文本。上游错误若包含其他凭证、内网地址或业务正文，仍可能进入持久化摘要或日志。本轮合成地址和假密码通过 safeFailure 原样返回。technicalFailure 还直接摘取底层异常消息，不能从方法名推断安全。

修复方向：对外/入库摘要用受控错误类别生成，原始异常不得默认传播。服务端诊断按明确允许字段记录，不用普通正则“脱敏一下”后保存整段任意报文。回归包含授权码变体、地址、假密码、多行及数据库异常。

### R12 / P2：管理默认参数可维护，却没有业务读取路径

位置：`CodeParameterDefinitionRegistry.java:29`、`:41`；目录及批次 Query 构造器；`ManagementAuditQuery.java`；`docs/decisions/默认参数与系统字典当前约定.md`。

注册并保存的两个默认参数，在生产 Java/管理前端中未找到按键读取并应用的路径。查询对象仍使用固定 20/100，文档中的列表默认值为 10。配置维护成功不代表列表行为变化。

修复方向：确定哪些入口确实受配置影响、环境如何确定，然后统一解析缺省值；显式请求值应保持优先。若功能尚未接入，应明确标记未生效，不把可编辑元数据当成运行功能。补“修改参数后默认查询变化”的端到端用例。

## 设计与规范问题

### R13 / P2：仍有两个完全原样复制的同步结果模型对

`HospitalDirectorySyncResult` 与 `HospitalDirectorySyncResultVO` 同为 12 个字段；`MedicalDirectorySyncResult` 与 `MedicalDirectorySyncResultVO` 同为 13 个字段。批次 Service 的 `toDirectoryResultView` / `toMedicalDirectoryResultView` 逐项原样复制，未做敏感信息隔离、时间转换或字段筛选。

修复方向：按实际读写契约复用一个已有结果类型；如需独立对外契约，必须说明当前真实差异，不以“分层需要”作为唯一理由。不能把所有 Record/VO 一概合并：凭证隔离、UTC 转换、协议字段与业务含义不同的对象有保留价值。

### R14 / P2：Mapper 长参数列表没有利用已有聚合事实

`HospitalDirectorySyncMapper.finishCompleted` 有 14 个参数，`MedicalDirectorySyncMapper.finishCompleted` 有 15 个参数，大量相邻 long 计数；已有 `MasterDataBatchCounts` 却未在此使用。`deleteRelationsForType` 还传入 SQL 完全未使用的 batchId。`finishFailure` 在生产 Java 中仅有声明、无调用。

修复方向：优先用现有计数类型表达一组业务事实，保留必要批次状态和审计字段；删掉确认未使用的参数及死入口。不为消除参数数量新增一套通用 Command/Context 包装层。

### R15 / P2：重复异常工具逻辑仍未复用 Func

两类同步 Service 的 `technicalFailure` 各自沿 cause 链循环；工程已有 `Func.rootCause/rootMessage`，基础实现带环检测。这里不仅重复，而且遇到 A→B→A 的 cause 环会循环不止。

修复方向：通用异常遍历复用已有工具，业务安全摘要另按 R11 处理；不能认为调用 `Func.rootMessage` 后消息就自动安全。正常承载同步事务、关系规则、协议转换的私有方法应保留，不能按 private 数量机械删除。

### R16 / P2：Javadoc 仍有模板空话和错误契约，表注释检查有盲点

- 7 个不含密码字段的 DTO 构造器仍写“密码等敏感原值不作裁剪”：CreateRoleCommand、UpdateRoleCommand、UpdateUserCommand、CreateDictionaryTypeCommand、UpdateDictionaryTypeCommand、CreateDictionaryItemCommand、UpdateDictionaryItemCommand。
- `OrganizationService.findAll` 注释说“当前调用方可见”，实际是无范围全量查询，容易误导后续调用者。
- 关系保留、摘要安全、批次成功审计等注释与实现不符，具体见 R01、R06、R11。
- `EncryptedExternalEndpointCredential` 是实际 Mapper 写入载荷，但类注释没有对应 `dbo.sys_external_endpoint_credential` 及表业务说明。
- 注释检查器自动发现 result 类型并核对手工登记清单，不能自动穷尽 SQL 写入参数模型，更不能证明文字业务含义准确。

修复方向：按方法实际业务作用重新写第一句话；只有关键数据后果才追加解释；简单构造器不要套不相关模板。持久化类型同时检查读模型和写载荷。格式校验继续保留，但语义要用调用链和反例验证。

## 待 SQL Server 并发验证的两组风险

### W01：新增机构会用旧快照整体覆盖用户机构授权

`OrganizationAdministrationServiceImpl.create:87` 读取创建人的所有机构 ID，加一个后调用 `replaceUserOrganizations`。与另一新增机构或权限撤销并发时，旧列表可能覆盖新授权，甚至恢复已经撤销的机构范围。这里未采用用户管理路径的同一锁定协议。

建议优先用现有单条授权语义追加新机构，验证与授权撤销的顺序；不要读全量后整体写回。需在真实 SQL Server 下分别验证阻塞、死锁、丢失更新和撤销不被恢复。

### W02：机构父链检查与更新没有跨节点并发保护

`OrganizationServiceImpl.validateParentChain:151` 普通读取父链后更新当前节点。A 改挂 B、B 改挂 A 同时执行时，各自 rowversion 只保护本行，不能独立证明两节点不成环。现有单线程 Mock 测试不覆盖此情形。

需在 SQL Server 2012 SP4 下验证现有隔离级别与锁行为，再决定统一树修改锁或其他有界并发协议；不能简单把所有查询改为 SERIALIZABLE 就宣称解决。

## 已改善且不应回退的部分

- 当前两类目录分页入口直接绑定各自 Query，不再保留 PageRequest→Query 原样复制。
- HTTP 基础约束使用绑定/Bean Validation，显式机构代码在入口检查；列表及按 ID 资源的范围约束在 SQL 中生效。按 ID 的范围查询不是应当删除的“多余鉴权”。
- 同步核心不再要求登录 principal；审计身份与权限检查分开。
- HIS 调用参数已收敛到 PhisInvocationContext，业务方法不再重复传 URI、超时和授权码。
- 医疗目录增量时间范围不再被当成全量，范围外旧记录不作缺失删除。

仍不能把 Service 中所有检查都挪到 Controller：数据库状态、并发版本匹配、关联完整性、HIS 响应校验及内部审计事实约束必须在其可信边界成立。目标是消除重复和职责错位，不是删除必要约束。
