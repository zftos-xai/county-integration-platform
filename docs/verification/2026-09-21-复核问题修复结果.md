## 中断收尾接口与行为

- 新增 `POST /api/v1/master-data/batches/{id}/recover`，请求复用 `{"version":"最近读取的Base64行版本"}`。
- HTTP 层要求 `master-data:sync`、有效会话、CSRF 与8字节版本；按ID查询仍带机构范围，范围外与不存在一致返回404。
- 仅 `FETCHING`、`RESULT_UNKNOWN` 且版本一致可收尾；状态或版本冲突返回409。每个写事务取得批次更新锁并核对版本，事务提交后释放。
- 收尾不调用 HIS，不补造未保存分项；缺少类型时以 `COMPLETED_WITH_UNKNOWN` 结束并释放活动范围。已保存分项全部成功才允许 `COMPLETED`。
- 原执行者若在外部取数，网络调用可能继续到完成或超时，但回到写事务后会因状态/版本不符被拒绝，不能覆盖已收尾结果。
- 同一批次不能直接重跑；需先核查来源交易再创建新批次。详情页提供权限控制、明确确认、重复点击保护及失败后回读提示，不自动重试。
- 此操作是有权限人员明确终止执行，不是自动判定执行者死亡，也没有实现租约或后台自动恢复。
- 对修改前遗留批次，历史分项缺失不能证明旧数据未更新；收尾只报告可证实事实，必要时在核查后新建同步重新对账，不能据缺失结果执行删除。

1. SQL Server 2012 SP4、兼容级别110：两个连接同时交叉修改父节点；第二个事务必须在首个提交后重新检查父链并拒绝成环。验证应用锁超时、失败回滚及权限；应用锁生命周期参考[Microsoft sp_getapplock 文档](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql)。未用文档代替实测。

3. 同步在某类型提交前、分项提交后、总结果提交前分别中断；验证目录数据与分项事实同进退。收尾与原执行者并行时，收尾提交后不能再写目录。

6. 真实 HIS 响应时序与受控失败，以及新收尾入口的浏览器交互、权限、409/网络中断回读；本轮没有浏览器或真实接口验收证据。
