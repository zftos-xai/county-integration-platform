# 基础数据原型评审（2026-09-19，历史记录，已废止）

> 2026-09-19 复核后，本评审中的“机构映射、验证批次、人工核查、人工发布”不再是有效业务设计。保留本文仅用于追溯错误决策；后续设计以[基础数据业务详细计划 2.0](../plans/基础数据业务详细计划.md)为准。

## 评审结论

本轮原型的业务骨架可以保留，暂不应按当前视觉和交互细节直接进入后端开发。

原型已经形成一条可解释、可追溯的基础数据业务链：

`平台当前数据 → 同步批次 → 异常事实 → 人工核查 → 新批次复核 → 正式版本`

四个页面各自解决一个真实问题，没有必要继续扩展新的一级页面：

- 数据目录：回答“平台当前保存了什么、HIS 当前能读什么”。
- 同步批次：回答“这次从哪里取得了多少、校验和发布到了哪一步”。
- 待核查问题：回答“为什么不能自动发布、谁处理、依据是什么”。
- 机构映射：回答“来源机构的数据应归到哪个平台机构”。

评审结果为：**业务方向通过，交互细节有条件通过；完成 P1 项后再冻结原型并拆后端任务。**

## 业务链评审

### 1. 数据目录：通过

优点：

- 先选机构，再选数据类型，符合县域平台按机构核对数据的使用方式。
- 当前数据与来源追溯放在同一记录详情里，能够同时看到来源系统、来源机构、来源记录标识、交易码和最近拉取结果。
- 明确区分“最近拉取”和“最近发布”，没有把接口调用成功直接等同于正式数据发布。
- 状态同时使用文字和颜色表达，不依赖颜色判断。

需要调整：

- 表格横向滚动后会失去批次号、机构或问题事实等上下文；关键识别列需要固定，操作列只保留一个入口。
- 目前存在行首展开图标和行尾“查看”两个等价入口，信息密度增加但没有增加能力。
- `9px–11px` 的辅助文字过多，医院管理和运维场景下长时间阅读困难。

### 2. 同步批次：通过

优点：

- `已发布 / 待核查 / 结果未知 / 未形成正式版本` 的分组能够直观说明业务影响。
- 批次详情没有把“返回 1,600 条”误判为完整成功，而是明确保留“结果未知”。
- 明确展示“不发布半批数据”“上一成功版本继续可读”“禁止直接重跑”，符合幂等与未知结果处理原则。
- 耗时格式符合约定：小于 1 秒使用毫秒，1 分钟内使用秒，超过 1 分钟使用分秒。
- 批次可以直接进入对应问题，链路连续。

需要调整：

- “来源声明 2,438 条”对非技术人员不直观，建议改为“HIS 告知总数 2,438 条”。
- “无独立行数接口”属于接口实现细节，列表中改为“总数未知”即可，技术说明放到详情。
- 展开详情后信息分成左右两块，但在 1280px 宽度下需要横向滚动，滚动后批次身份丢失。

### 3. 待核查问题：有条件通过

优点：

- 把事实、影响、请求标识、已有依据、联系人、最近核查、下次核查和下一步集中展示，足以支持交接。
- 明确“来源缺失不等于停用、结果未知不等于空数据”，避免错误覆盖正式数据。
- 管理人员只看影响，运维人员登记结论，职责边界合理。
- 登记结论不会直接发布数据，而是要求通过后续新批次重新取得、校验和发布，闭环正确。

必须补齐：

- 保存核查结果后的状态转换需要在原型中演示完整：保存后问题进入什么状态、下一次核查时间如何生成、何时允许创建复核批次、复核成功后问题何时关闭。
- “仍无法确认”和“已确认本批不完整”两个结论适合当前分页超时案例，但不能直接当作所有问题类型的统一选项；不同问题类型只显示其实际可用结论，避免造出庞大通用状态机。
- 角色切换后，侧栏仍显示“管理视角”，同时又显示“运维人员”，身份表达矛盾，必须统一。

### 4. 机构映射：通过

优点：

- 映射冲突不是直接覆盖，而是先展示 HIS 返回值与平台当前机构，再要求选择归属并填写可复核依据。
- 保存核对结果后只进入“待验证”，不会恢复日常同步，也不会自动改平台机构名称。
- 验证通过前保留既有正式数据，符合业务连续性要求。
- 流程控制在“核对归属 → 验证批次 → 恢复同步”三步，没有继续扩展成独立的机构主数据治理系统，范围合适。

需要调整：

- 冲突场景默认选中了原平台机构，容易让用户未经判断直接保存。冲突时应默认不选；已映射的只读查看场景才回显原值。
- “保存核对结果”应在平台机构或核对依据为空时禁用，并在字段旁直接说明原因，而不是点击后只弹顶部提示。
- 弹窗需补键盘焦点约束：打开后焦点进入标题或首个字段，`Esc` 关闭，焦点返回原“处理”按钮。

## 必须调整项

### P1：原型冻结前必须完成

1. **统一身份与权限表达。** 顶部“运维”被选中时，侧栏不能再同时显示“管理视角”。正式产品中角色来自登录权限，原型角色切换器只能作为演示工具，不能进入生产需求。
2. **解决表格横向滚动丢失上下文。** 固定第一项业务识别列，必要时固定操作列；展开详情应占据可视宽度，不随表格横向滚动偏移。
3. **提高基础字号。** 正文和表格内容原则上不低于 12px，关键事实不低于 13px；`9px–10px` 只允许用于极少量非关键标记。当前问题事实、映射依据、说明文字普遍偏小。
4. **补齐问题保存后的完整演示链。** 至少覆盖“继续等待来源方”和“确认本批不完整、创建新批次复核”两条路径，并展示最终关闭条件。
5. **冲突映射取消默认选择并做字段级校验。** 防止惯性确认错误机构。

### P2：进入前端实现前完成

1. 去掉表格首列展开按钮与末列“查看”的重复入口，统一使用一个明确动作。
2. 简化技术文案：将“来源声明”“无独立行数接口”等改成业务可理解的说法，技术字段留在详情。
3. 处理侧栏与页面内二级导航重复。建议保留侧栏作为一级入口，页面内只保留带数量的关联跳转，不再表现为第二套相同导航。
4. 所有关键按钮和图标按钮的可点击区域达到约 44×44px；当前多个 28–35px 控件偏小。
5. 验证弹窗焦点圈、键盘顺序、Esc 关闭、关闭后焦点回归，并在 200% 缩放下复验表格和表单。

### P3：联调前补充

1. 为无数据、加载失败、无权限、会话失效、并发冲突分别提供页面状态。
2. 批次和问题详情增加“最近刷新时间”，避免用户把旧页面当作实时结果。
3. 真实数据量接入后复核筛选性能、分页策略和长机构名称/长编码展示。

## 明确不做，防止过度设计

- 不新增“任务中心”“数据治理中心”“审批中心”等一级模块；现有四个页面已经覆盖首批基础数据闭环。
- 不允许在平台页面直接修改 HIS 来源业务字段。
- 不把“人工确认”设计成数据发布；人工只登记事实和依据，正式数据仍由新批次校验发布。
- 不为所有异常建立一套万能处理表单；根据问题类型显示少量、明确的处理结论。
- 不把原型角色切换器、演示账号、演示时间和模拟状态带入正式认证与授权设计。

## 原型冻结标准

完成以下验证后，本轮原型才可以冻结：

- 管理人员能够从数据目录找到一条数据的来源和当前可读版本。
- 运维人员能够从结果未知批次进入具体问题，登记依据并形成明确下一步。
- 核查结果不会直接发布数据，复核批次成功后才更新正式版本。
- 机构映射冲突必须经过人工依据和验证批次，不能直接恢复同步。
- 1280px 桌面宽度和 200% 缩放下，关键身份、问题事实、状态和操作仍可见、可读、可操作。
- 键盘可以完成页面导航、展开详情、填写表单、关闭弹窗并回到原触发位置。

## 2026-09-19 基础数据业务一致性复审

### 复审结论

结合《业务功能完成与验收标准》《基础数据业务详细计划》和《新版基层HIS 与云平台V1.0接口文档》再次复审后，现有四个页面和异常闭环仍可保留，但原型暂不能冻结。

本轮结论为：**页面结构通过，异常处理方向通过，数据范围和字段口径有条件通过。** 在开始正式页面和后端持久化实现前，必须先修正下列业务语义，否则会把原型中的演示假设固化成数据库结构和接口契约。

### 真实业务链

基础数据不是“调用成功后把结果显示出来”，而是以下完整链路：

`机构接入就绪 → 确定数据范围 → 创建同步批次 → 按交易与查询条件取得 → 暂存和校验 → 数量及关系核对 → 原子发布 → 县医院HIS读取 → 三方数量验收`

各页面在链路中的职责保持如下，不新增一级模块：

| 页面 | 回答的问题 | 不承担的职责 |
| --- | --- | --- |
| 数据目录 | 当前正式发布了什么，数据从哪里来，县医院HIS当前能读什么 | 不修改HIS来源字段，不处理未发布暂存数据 |
| 同步批次 | 某个机构、数据类型和查询范围取得了多少，是否完整发布 | 不把一次接口成功直接等同于业务发布成功 |
| 待核查问题 | 哪个事实阻止发布，谁核查，依据和下一步是什么 | 不人工补造来源数据，不直接发布数据 |
| 机构映射 | `100-008`来源机构应归属哪个平台机构 | 不借映射修改平台机构权限和主数据 |

| 公共字典 | 当前接口资料没有公共字典查询接口 | 原型基础数据目录未展示 | 处理正确；继续标记“接口资料不完整”，不得拿平台自身数据字典冒充来源同步结果 |

### 原型冻结前必须修正的业务口径

1. **修正时间字段。** `100-003`和`100-008`返回中没有来源更新时间，数据目录中的“来源更新时间”不能显示为确定事实。统一改为“平台最近取得时间”；只有`100-004`和`100-006`返回的创建时间才能标为“来源创建时间”，且不得解释为更新时间。
2. **拆清`100-003`的四个调用范围。** 批次详情至少展示科室、医生、病区、床位四个子范围的返回数、校验结果和交易请求标识。是否四类一起原子发布，需要业务方确认；确认前按数据类别分别发布更安全。
3. **重新确认ICD10归属范围。** 接口文档没有机构参数。未取得实际WSDL和脱敏样例前，原型不得宣称某机构拥有一套独立ICD10；机构筛选下应显示“平台公共目录”或暂不展示。
4. **中药、西药分别展示。** 两者是不同目录类型，不能用一个“药品”标签合并数量、停用状态和验收结果。诊疗、耗材也分别形成自己的批次和当前版本。
5. **把“全量”改为可证明的范围。** `100-004`和`100-006`的开始、结束时间为必填，但文档未说明按创建时间还是更新时间过滤。未确认前，批次应展示确切时间范围并称“约定范围”，不能直接声称已取得全量。
6. **补齐三方核对。** 现有批次详情已有HIS总数、实际返回和HIS可读取结果，但还缺同一范围内的“来源实际返回数、平台当前有效数、县医院HIS读取数”并列结果和验收人。三者必须带机构或公共范围、数据类型、查询时间、版本和批次号，不能只对三个总数。
7. **区分两个HIS角色。** 页面中的“基层HIS”是来源系统，“县医院HIS”是平台正式数据的只读消费方。所有“HIS可读取”文案改为“县医院HIS可读取”，避免用户误以为数据又回写到来源HIS。
8. **补齐业务验收责任。** 每个已发布数据类型需要显示来源确认人、平台核对人、县医院HIS验收人及验收时间；这是完成标准，不扩展成审批中心。

### 各页面的下一轮调整边界

#### 数据目录

- 数据分类调整为：机构资料、科室、人员、病区、床位、中药、西药、诊疗、耗材、ICD10；疫苗、血液仅在业务确认纳入后出现。
- 在表头和详情中按接口能力区分“平台最近取得时间”和“来源创建时间”。
- 详情中的交易名称应随数据类型变化，不能所有记录固定显示`100-003 · 基础数据查询`。
- 增加轻量的验收结果区：平台当前有效数、县医院HIS读取数、最近核对时间、验收人；不新建一级“验收中心”。
- ICD10在归属范围确认前从机构目录移出，避免形成错误的数据所有权暗示。

#### 同步批次

- `100-003`聚合任务展开后展示四个目录类型的调用结果；单类复核批次继续只显示对应类型。
- `100-004/100-005`和`100-006/100-007`详情补充完全一致的查询条件、分页范围和请求标识，以证明行数与分页数据属于同一业务范围。
- 将“全量分页”改为“约定时间范围分页”，直到来源方确认时间字段语义、边界、时区和迟到数据规则。
- 增加“平台发布后有效数”，与本批发布数区分；新增、更新和未变化数不能代替当前有效总数。
- 首次同步入口只在机构映射、接口配置和数据范围均就绪时向有权限的运维人员开放；相同范围已有活动批次时禁止再次发起。

#### 待核查问题

- 当前的来源缺失、分页结果未知、数量不一致、关系冲突和未定义取值五类问题足以覆盖首批场景，继续按类型提供少量结论，不增加万能表单。
- 增加“查询范围”事实，特别是目录类型、开始结束时间、诊断版本和疾病类别，保证复核批次确实重放同一范围。
- 对`100-003`人员关系冲突，在一人多科室规则未确认前不得把“单一所属科室”作为既定事实；应先标记为“关系规则待确认”。

#### 机构映射

- 来源机构代码明确标注为`100-008`返回的机构ID；平台机构代码继续作为独立字段展示。
- 首次验证批次只验证机构身份和归属，不发布其他业务目录；当前原型边界正确。
- 映射完成不等于业务数据可用，仍需逐类完成首次成功批次和三方数量验收。

### 防止过度设计

- 不新增数据治理中心、任务中心、审批中心或独立验收中心。
- 不为了统一页面而把所有基础数据塞进一张万能表；页面可统一，业务键、字段、关系和版本必须按数据类别定义。
- 不为接口未提供的更新时间、停用状态、机构维度或全量语义造字段、造状态、造结论。
- 不在原型中模拟已经完成真实联调；所有合成数量继续明确标记为演示数据。

### 开发前正式业务形态收口

为避免开发阶段继续沿用“只看演示数据”的页面结构，本轮补齐以下开发基线：

- 数据目录按归属拆成“机构基础数据”和“平台公共目录”。ICD10进入公共目录待确认态，不再通过临时提示依附某一家机构。
- 同步批次形成正式发起入口：运维人员选择一个已完成映射和接口配置的机构，再选择一个数据类型；创建前明确检查机构映射、接口启用状态及同范围活动批次。
- 新批次从“取得中”开始，取得、校验和发布完成前不改变当前正式版本；失败、结果未知和待核查仍沿用上一成功版本。
- 批次列表收敛为批次范围、机构范围、交易及返回、业务问题、状态及时间、操作六组信息，列表内容保持单行，完整事实进入展开详情。
- 管理视角只查看和确认业务影响，发起同步需明确切换到运维视角；原型角色仅用于评审，正式实现仍由服务端权限控制。

正式开发必须把页面中的三项就绪检查实现为服务端实时判断，不得把原型中的勾选结果当作可信状态；创建批次还需使用机构、数据类型与查询范围组成活动任务唯一约束。
