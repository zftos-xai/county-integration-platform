## 1. 本轮目标

本轮把已评审原型转换为正式开发边界，先固定页面职责、批次领域语言和接口契约，再进入数据库及业务实现。原型只用于确认业务形态，正式页面不得引用原型数据、原型组件状态或浏览器本地存储。

首个纵向切片选择“同步批次”，因为数据总览、待核查问题、机构映射验证和正式数据发布都依赖同一批次事实。首个切片未完成真实持久化、服务端授权、测试和构建前，不加入正式菜单。

## 2. 正式前端页面拆分

| 页面 | 地址 | 页面直接回答的问题 | 首批主要操作 | 明确不做 |
| --- | --- | --- | --- | --- |
| 数据总览 | `/master-data` | 每类数据最近成功是什么、平台有多少、县医院HIS能读多少 | 筛选机构、查看正式数据、进入最近批次和读取状态 | 不直接编辑来源数据，不展示未发布暂存数据 |

数据明细和县医院HIS读取状态作为数据总览的二级页面，不增加一级菜单。正式页面目录按业务职责就近组织：

```text
web-admin/src/views/master-data/
├── overview/       数据总览、正式数据详情、县医院HIS读取状态
├── batch/          同步批次列表、批次详情、发起同步
├── issue/          待核查问题列表和处理抽屉
└── mapping/        来源机构映射列表和编辑抽屉
```

页面公共部分只提取确实跨页面复用的机构筛选、状态标签和分页组件，不建立万能“基础数据页面”组件。列表默认单行展示，长内容省略并提供完整查看；操作列固定，详情使用抽屉或独立二级页。

## 3. 后端批次领域边界

后端使用单独的`masterdata`业务包，不放回`his`协议包或`exchange`交易日志包：

```text
cn.zqkj.platform.masterdata
├── controller       正式管理API和县医院HIS只读API
├── domain
│   ├── dto          查询条件、创建批次、核查和映射命令
│   ├── model        批次、状态、数量、问题、映射及强类型业务模型
│   └── vo           页面和HIS读取所需的明确输出
├── mapper           MyBatis Mapper接口
└── service
    └── impl         状态迁移、暂存校验、发布和查询实现
```

包之间职责如下：

- `his`只负责按机构配置调用`PHIS_Interface`并返回强类型来源结果；不决定批次能否发布。
- `exchange`只记录一次外部交易调用的运行事实；不能代替同步批次。
- `masterdata`负责业务范围、批次状态、暂存校验、数量核对、问题处理、原子发布和正式数据读取。
- `system`继续负责平台机构、外部系统配置、用户、权限和审计；机构映射不能反向改变用户数据范围。

### 3.1 批次状态

正常状态链固定为：

`CREATED → FETCHING → VALIDATING → READY_TO_PUBLISH → PUBLISHED`

异常分支为：

- `FAILED`：已确认失败，本批次终止，上一正式版本继续可读。
- `RESULT_UNKNOWN`：未取得可证明的最终结果；先读取交易和批次事实，不能直接再次提交。
- `PENDING_REVIEW`：存在来源缺失、关系冲突、未知取值或数量不一致，处理后回到`VALIDATING`重新校验。

只有`PUBLISHED`可以成为当前正式版本。`FAILED`和`PUBLISHED`为终态；重新同步必须创建新批次并保留原批次证据。

### 3.2 首批数据类别

首批类别固定为机构资料、科室、人员、病区、床位、中药、西药、诊疗、耗材和ICD10。疫苗、血液和公共字典未完成范围确认，不提前加入枚举或页面筛选。

- 机构资料使用`100-008`。
- 科室、人员、病区和床位分别形成独立业务类别，来源调用均使用`100-003`，一次请求只传一个目录类型。
- 中药、西药、诊疗和耗材分别形成独立业务类别，使用相同范围的`100-005`声明数量和`100-004`分页取数。
- ICD10使用相同范围的`100-007`声明数量和`100-006`分页取数；机构维度未确认前按平台公共范围管理。

### 3.3 数量口径

批次必须分别保存来源声明数、实际取得数、重复数、无效数、冲突数、新增数、更新数、未变化数、来源缺失数和发布后平台有效数。来源未提供数量接口时，声明数必须为空，不能用实际取得数伪装。

## 4. 第一版接口契约

所有接口使用`/api/v1`前缀、统一`ApiResponse<T>`信封、服务端功能权限和机构范围校验。所有列表使用真实分页；时间使用带偏移的ISO 8601输入，进入数据库前统一转换为UTC。

### 4.1 同步批次

| 方法和地址 | 权限 | 用途 | 关键约束 |
| --- | --- | --- | --- |
| `GET /master-data/batches/options` | `master-data:sync` | 读取当前账号可用的HIS机构、环境和已实现同步业务 | 来源必须对应启用且接入信息可解析的机构接口配置；业务由后端能力注册返回，页面不得写死交易码或目录类型 |
| `GET /master-data/batches` | `master-data:read` | 按机构、请求标识、类别、状态和开始时间分页查询 | 公共目录不强制机构参数；只返回调用人有权查看的机构；结果未知时可按请求标识精确回读 |
| `GET /master-data/batches/{batchId}` | `master-data:read` | 读取一条批次最新事实 | 只读，不因查看详情触发重试或状态迁移 |
| `POST /master-data/batches` | `master-data:sync` | 创建一个范围明确的同步批次 | 要求请求标识；同范围存在活动批次时返回冲突 |
| `POST /master-data/batches/{batchId}/fetch` | `master-data:sync` | 通过100-003取得科室并完成暂存校验 | 仅支持科室类型0；携带最近批次版本；外部调用不占用数据库事务；不自动发布 |
| `POST /master-data/batches/{batchId}/publish` | `master-data:publish` | 发布已校验的科室正式版本 | 仅允许`READY_TO_PUBLISH`；携带最近批次版本；发布使用短事务，失败回滚且保留上一正式版本 |

创建请求字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `requestKey` | 是 | 客户端为一次用户操作生成的稳定请求标识，用于超时后回读，不作为业务批次号 |
| `organizationCode` | 机构范围必填 | 平台机构代码；ICD10公共范围为空 |
| `environment` | 是 | 本批精确使用的开发、测试或生产接口配置环境 |
| `category` | 是 | 已登记的首批数据类别 |
| `sourceType` | 按接口 | `100-003`或`100-004`的目录类型；必须与类别匹配 |
| `rangeStart`、`rangeEnd` | 分页目录必填 | 原样记录的来源查询时间范围；语义未确认前不称为更新时间范围 |
| `diagnosisCategory`、`diagnosisVersion` | ICD10必填 | `100-006/100-007`必须一致的查询条件 |

批次摘要响应必须包含：平台批次主键、批次号、范围类型、机构、数据类别、数据及数量交易码、来源类型、查询范围、批次状态、全部数量口径、开始/结束/发布时间、可理解的失败摘要和数据库并发版本。响应不包含厂商编号、验证码、账号、密码、SOAP原文或完整来源正文。

## 5. 实施顺序与退出条件

1. **契约和状态模型。** 前后端状态、类别、数量和路径测试通过；这是本轮已开始的切片。
2. **`V0600`持久化底座。** 建立批次、问题、映射、暂存和正式表；SQL Server 2012约束能够阻止同范围并发活动批次。
3. **合成数据闭环。** 完成创建、暂存、校验、发布、失败回滚和重启恢复测试；不调用真实患者数据。
4. **同步批次正式API和页面。** 页面只调用真实API，覆盖加载、空数据、失败、无权限、并发冲突和结果未知。
5. **总览、问题和映射。** 复用已经验证的批次事实分别实现，不增加审批中心、任务中心或万能数据表。
6. **正式菜单。** 真实API、权限、自动化测试和生产构建全部通过后，才加入“基础数据”分组。

第一切片退出条件是：Java状态模型测试、前端路径和类型检查通过，接口字段在前后端保持一一对应，并且没有把原型数据带入正式代码。它不代表同步业务已经完成，也不作为真实联调证据。
