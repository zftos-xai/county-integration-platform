# 原型设计与验证

- 日期：2026年9月16日
- 阶段：项目启动前的交互原型
- 依据：[总体方案](../plans/总体方案.md)、[平台数据边界决策](../decisions/架构决策.md)
- UI框架：[系统 UI 布局框架](./系统UI布局框架.md)
- 结论边界：当前页面和合成数据只用于评审需求与交互，不代表真实接口、SQL Server、服务端权限、备份恢复或厂商联调已经完成。

## 1. 原型目标

原型帮助医院信息科、实施和运维人员在项目启动前确认三个问题：平台管理什么、每笔交换进行到哪一步、当前责任人可以执行什么操作。页面按总体方案中的基础数据处理和业务接口处理组织，完整系统关系不在本文重复维护。

## 2. 页面范围

| 分组 | 页面 | 评审目的 |
| --- | --- | --- |
| 工作台 | 运行总览 | 查看两类数据传递过程、未解决事项、运行摘要和快捷入口 |
| 基础数据 | 基础数据 | 查看机构、科室、人员、目录的来源、同步状态、平台保存情况和HIS读取状态 |
| 基础数据 | 同步记录 | 查看每次同步的时间、方式、数量、结果和处理依据 |
| 业务接口 | 业务接口 | 查看提供方、调用方、源目标系统、交易码、版本、运行控制和编码映射 |
| 业务接口 | 交换记录 | 按机构、业务单号和请求编号查看接收、发送、目标系统返回结果及数据状态 |
| 平台管理 | 机构与权限 | 管理接入机构、外部代码和接口范围 |
| 平台管理 | 告警管理 | 处理同步、接口、结果未知和清理失败告警 |
| 平台管理 | 审计记录 | 查询配置、视图发布、核查和处置操作 |

核心页面先提供可搜索、筛选和分页的列表，再从单条记录进入详情和当前允许的动作。交换详情采用“概况、数据版本、发送请求、处理记录”四类信息，业务结果、任务进度和数据保存状态分别展示。

运行总览采用标准运行工作台结构：第一层只显示启用机构、允许新请求的接口、待核查交换和待处理告警；第二层直接列出告警工作队列与待核查交换。总览不再重复展示业务数据传递过程说明、状态分布和接口清单，详细信息从对应业务页面查看。

基础数据页面以可操作列表为主要内容，只保留“基础数据”和“同步记录”两个一级页签。HIS读取不作为独立页面：列表按每类数据显示“可读取、待开放、未开放”，来源字段、停用规则、保存字段及执行历史进入单条详情查看；数据库视图名、读取账号、范围和配置版本只在单条详情的“HIS读取”页签中提供给实施和管理人员核对。

业务接口与交换记录通过交易码建立关联。每笔交换记录还要固定保存受理时的接口名称和规则版本，形成历史规则快照；后续修改当前接口定义时，不覆盖历史交换记录。交换列表可以按业务接口筛选并进入接口定义，接口详情可以反查使用该接口的交换记录。交易码相同但调用方向不符合当前定义时显示“方向待核实”，不能直接判定为关联正确。

接口当前状态决定是否允许新请求。“已启用”允许正式接入，“演示启用”只用于原型检查；“接口资料不完整”“待联调”和“已停用”都阻止新请求进入。允许新请求后，新交换记录采用接口当前版本；已有记录仍使用各自受理时保存的规则。接口异常告警按交易码汇总受影响的交换记录，并允许从告警直接进入单笔记录核查。

## 3. 角色与操作边界

| 角色 | 允许操作 | 禁止操作 |
| --- | --- | --- |
| 管理人员 | 查看基础数据和运行情况；维护机构权限、接口版本、状态及编码映射 | 代替业务系统完成诊疗；修改交换结果或患者业务正文 |
| 运维人员 | 跟踪交换、领取核查、登记证据、执行受控重试和处理告警 | 在结果未知时直接重发；绕过校验；修改业务正文 |

县人民医院和基层卫生院是交换两端，不作为平台后台操作角色。正式系统必须在服务端校验身份、机构范围和操作权限，前端隐藏菜单不能作为权限控制。

## 4. 关键交互规则

1. 已受理仅表示平台接收请求，不表示目标系统处理成功。
2. 外部调用超时进入“结果未知”，先查询目标系统处理结果或目标系统返回结果，不能直接重发。
3. 同一业务的不同版本分别记录；不得用来源最新版本替换已受理请求的原版本。
4. 业务状态与正文保存状态分开；清理正文不改变业务结果。
5. 人工处理必须填写依据、说明和下一次核查时间，所有动作进入审计。
6. 基础数据来源、停用含义、视图字段或权限未确认时显示“接口资料不完整”，不展示为已发布。
7. 页面不提供真实患者身份、病历、报告正文、生产地址、密码、令牌或数据库凭证的查看和导出入口。
8. 接口定义负责说明当前规则；交换记录负责保留当时采用的规则快照。两者可以互相定位，但当前配置变更不得回写历史记录。
9. 创建交换记录前必须根据接口状态判断是否允许新请求；被阻止的请求不生成新的交换记录。
10. 接口异常先确定受影响记录范围，再分别核查业务结果；接口恢复本身不能批量改写这些记录的业务结果。

## 5. 启动前验证场景

| 编号 | 场景 | 必须验证的结果 |
| --- | --- | --- |
| S01 | 已受理后平台重启 | 未可靠保存不得回复已受理；恢复时不产生重复写入 |
| S02 | 发送超时且结果未知 | 有权威证据后才确认结果；查询无结论时保持未知 |
| S03 | 报告旧版失败后出现新版 | 新旧版本独立，禁止静默替换和版本倒退 |
| S04 | 正文清理后重复提交 | 能识别已处理业务并返回原结果引用，不再次写入 |
| S05 | 查询时来源系统停机 | 明确区分不可用、超时、无数据和无权限 |
| S06 | 正文到期但业务未完成 | 到期停止新发送并按批准规则清理，业务结果单独保留 |
| S07 | 两端数量相同但版本或结果不同 | 按稳定业务键逐条核对，不以总数相同判定一致 |
| S08 | 从旧备份恢复平台 | 恢复环境先停写并核查备份点后的目标结果 |
| S09 | 来源只能提供最新版本 | 无法证明原版本时阻止自动恢复，不用新版代替旧请求 |
| S10 | 查看、导出及越权 | 服务端拒绝跨机构访问，日志和浏览器存储不泄露敏感正文 |
| S11 | 清理失败或与发送并发 | 到期后不开始新发送；失败可见、可重试且不会部分静默完成 |

S01、S02、S03和S06是首批高风险场景，应优先完成交互评审；S04至S11在真实接口和数据库条件具备后纳入完整验证。

## 6. 验证层级与证据

| 层级 | 项目启动前可做 | 项目实施后补充 |
| --- | --- | --- |
| 业务规则 | 用合成数据走查状态、动作和禁止条件 | 由业务负责人确认真实流程和成功含义 |
| 前端原型 | 类型检查、生产构建和浏览器交互 | 接入真实身份与服务端权限后做越权验证 |
| 接口规则 | 核对参考文档中的方向、字段和冲突 | 使用正式WSDL/OpenAPI、已删除或遮盖敏感字段的样例和真实目标系统返回结果验证接口规则 |
| 数据库 | 审查SQL Server 2012兼容设计 | 在SQL Server 2012 SP4兼容级别110执行迁移、并发、清理和恢复测试 |
| 从页面请求到目标系统结果 | 形成测试用例和验收记录模板 | 在授权环境与双方厂商联调并取得书面验收 |

一次正式实验至少记录：场景与接口版本、前置数据、机构与角色、执行步骤、期望结果、实际结果、请求编号、配置版本、时间、日志或数据库证据、缺陷编号、复测结论和确认人。生产敏感正文不得作为普通测试附件。

## 7. 当前原型数据

演示数据位于`web-admin/src/prototypeData.ts`及相关页面组件，只由`/prototype`使用。所有`SIM-*`、`DESIGN-*`编号，机构、账号、视图名称、时间、数量和目标系统返回结果均为虚构，可以通过“重置原型数据”清除。

已有本地规则测试和前端构建结果只能证明代码能够按合成场景运行。项目尚未启动，因此不使用“项目验收通过”“接口完成”或“生产可用”等结论。

## 8. 后续完善顺序

1. 先确认总体方案、角色、范围、正式数据来源和视图规则。
2. 继续核实每项接口的交易码、调用方向、提供方、规则版本、启停条件和成功条件，清除“方向待核实”记录。
3. 按真实使用人评审导航、字段、筛选、详情和操作用语。
4. 建立服务端身份与机构权限后，替换浏览器本地状态。
5. 选取一项已批准接口接入正式接口说明和已删除或遮盖敏感字段的样例。
6. 在SQL Server 2012 SP4环境验证迁移、并发、清理、备份和恢复。
7. 完成S01至S11验证并留存证据后，再更新为阶段验收结论。

## 9. 核心对象和状态规则

业务接口定义当前允许接入的规则；交换请求固定保存受理时规则快照；一次交换请求可以产生发送尝试、业务结果、临时数据和运行告警。发送尝试的技术状态不得直接替代业务结果，临时数据的清理状态也不得改写业务结果。

```text
业务接口
→ 交换请求（保存受理时规则版本）
→ 发送尝试（可以有多次技术执行）
→ 业务结果（成功、明确失败、结果未知或被规则拦截）
→ 临时数据状态（未保存、临时保存、到期、清理失败、已清理）
→ 运行告警或人工跟踪事项
```

每个详情页面必须说明当前状态的进入原因、允许动作和禁止动作。结果未知禁止直接重发；版本不一致禁止用新版覆盖原请求；数据到期必须先停止发送再清理；平台重启后必须先完成恢复检查。

## 10. 告警聚合和责任时限

同一问题类型和同一业务对象在未恢复前归入同一个告警事项。告警至少保存首次发生时间、最近发生时间、累计事件数、当前责任人、应处理时间和受影响记录范围。接口恢复只能关闭技术故障，不批量改变受影响交换记录的业务结果。

告警列表的等待时长和应处理时间必须来自告警数据，不得根据列表位置临时计算。领取、转交、持续观察和完成处理都需要记录责任、期限和审计证据。

## 11. 配置保存、启用与影响检查

接口配置不建立独立的多级审批和发布任务。规则修改保存后进入“待联调”并阻止新请求；完成必要核对后，由管理人员单独启用当前版本。运行异常时可以立即暂停新请求。

保存前影响检查至少展示：变更字段、当前授权机构、历史涉及机构、未完成交换、是否允许新请求的变化和历史记录所用规则的处理方式。历史涉及机构多于当前授权机构时必须提示核对，不能自动推断为权限错误或自动恢复授权。

## 12. 发送尝试与业务结果证据

一笔交换请求可以产生零次、一次或多次发送尝试。每次尝试分别记录尝试编号、开始时间、执行阶段、技术结果、目标响应摘要和证据编号。发送尝试只说明技术执行过程，不直接代表业务成功。

业务结果按下列证据判定：

| 结论 | 必要证据 | 不足以单独判定的内容 |
| --- | --- | --- |
| 已确认写入 | 目标系统业务成功码和目标系统返回结果编号，或按相同业务键与版本查询到目标记录 | HTTP 成功、网络连通、消息发出成功 |
| 明确未写入 | 目标系统按业务键与版本查询的无记录结果，或明确失败目标系统返回结果 | 本地超时、连接失败、平台重启 |
| 结果未知 | 未取得上述任一类有效证据 | 推测、口头反馈或仅有平台发送日志 |
| 规则拦截 | 发送前校验记录证明未调用目标系统 | 规则拦截不能证明业务成功 |

## 13. 配置版本恢复

保存前按字段展示当前值与拟保存值，重点核对规则版本、状态、数据范围、服务地址、超时、重试、重复识别、成功判定和数据保存策略。操作人必须填写变更、启用或暂停的依据。

历史配置只能载入为恢复草稿。载入后接口状态改为“待联调”，当前运行配置保持不变；管理人员核对影响并保存后，才能另行启用。恢复历史配置不得覆盖已有交换记录保存的规则快照。

## 14. 告警责任与持续观察

普通告警和接口故障告警采用相同的责任落实过程：当前责任人、完成期限、下次检查时间、处理依据和当前状态必须同时保存。保存处理进展只更新告警跟踪信息，不改变关联业务结果。仍有未完成清理或证据不足的事项时，不允许直接完成告警处理。

## 15. 批量操作边界

当前原型不建设通用批量处理中心。仅允许批量分配告警责任人、调整处理期限和导出获批范围内的记录摘要。批量确认业务成功、批量重发结果未知记录、批量清理数据、批量启停接口和批量恢复历史配置均不提供入口。

## 16. 状态名称与页面边界

原型统一采用《系统UI布局框架》中的全系统状态词表。交换记录同时展示“业务结果”“处理进度”和“数据保存”，三者不得压缩为一项：业务结果回答目标系统是否完成业务处理，处理进度回答当前事项走到哪一步，数据保存回答平台是否保存正文以及是否需要清理。

告警状态只表示告警事项是否已确认、正在处理或已经恢复；关闭技术告警不得自动把关联交换记录改成“已确认写入”。接口运行状态只决定是否允许新请求；修改接口状态不得覆盖历史交换记录保存的受理时规则和业务结果。

## 17. 高优先级和中优先级业务优化结果

本轮按六个方面完善原型：

1. 每个异常详情显示处理方式、进入原因、允许动作和禁止动作。系统处理、人工核查、运维处理和外部协同分别展示，人工操作不得修改来源业务数据。
2. 接口技术故障与交换业务结果分别处理。接口恢复并通过受控验证后可以结束技术告警；结果未知的记录仍须单独核查，并记录责任人和完成期限。
3. 机构接口权限区分已配置和当前有效。当前有效必须同时满足机构启用、接口启用、权限已批准、批准依据完整且在有效期内。
4. 接口启用前检查调用关系、身份验证、数据范围、保存策略、服务地址、执行控制、成功判定和有效机构权限；规则变更仍采用“保存为待联调，再单独启用”的轻量流程。
5. 告警等待时间、应处理时间和逾期时间按首次发生时间、优先级和演示截止时间计算。业务核查、数据清理和告警变化同步更新关联对象并写入审计记录。
6. 基础数据执行记录补充批次范围、来源版本和下次执行时间；HIS读取详情指向当前成功批次。审计详情按字段展示变更前后差异。

上述结果只验证业务逻辑和页面交互。正式时限、权限批准依据、接口参数、来源版本以及真实运行结果仍需在实际环境确认。
