# SQL Server 建设与迁移脚本规范

本规范适用于平台数据库的建表、约束、索引、数据修复和 Flyway 迁移脚本。数据库统一为 Microsoft SQL Server 2012 SP4、兼容级别 110。任何自动检查只能证明静态规则通过，不能替代同版本数据库验证。

## 1. 一个业务一个主版本

- 一个业务域只能有一个当前主版本脚本，主版本集中建立该业务已经确认的表、字段、约束和首批索引。
- 主版本必须来自已确认需求和数据边界；不得为尚未选定的接口、原型页面或通用平台设想预建表和字段。
- 主版本尚未进入共享环境时，发现遗漏或错误必须直接收敛主版本，不得连续新增补丁掩盖尚未稳定的设计。
- 主版本通过正式数据库基线评审并进入不可重建的共享环境后禁止修改，只能增加归属于该主版本的补丁。开发联调库不等同于正式共享基线；基线评审前发现问题必须修改主版本并重建开发库，不得用补丁掩盖未稳定设计。
- 不同业务域不得共用一个笼统的`platform_baseline`脚本；跨业务公共对象必须先明确唯一责任模块，再作为独立业务域管理。

## 2. 版本和文件命名

Flyway版本号全局递增，使用四位数字。业务名和动作名只使用小写英文字母、数字和下划线。

主版本格式：

```text
V<全局版本>__<业务域>_main.sql
```

示例：

```text
V0100__exchange_main.sql
```

补丁格式：

```text
V<全局版本>__<业务域>_V<归属主版本>_patch_<补丁序号>_<动作>.sql
```

示例：

```text
V0101__exchange_V0100_patch_001_add_result_index.sql
V0230__exchange_V0100_patch_002_extend_result_code.sql
```

全局版本保证 Flyway 始终按提交顺序执行；文件名中的`V0100`明确补丁归属的业务主版本。不得使用会排在已执行迁移之前的`V0100.001`等版本方式，也不得使用`fix`、`update2`、`final`等无法追溯的名称。

## 3. 补丁膨胀控制

- 每个业务主版本默认最多保留 5 个补丁；达到上限前必须评审根因和合并策略。
- 同一主版本的补丁序号从`001`连续递增，不得复用、跳号或改变已有补丁含义。
- 一个补丁只处理一个可说明、可验证、可回退的数据库变更，不夹带其他业务修改。
- 尚未进入共享环境的补丁必须合并回主版本并删除补丁文件。
- 进入下一正式数据库基线时，已执行补丁应形成归档清单；不得通过复制全部历史DDL制造新的膨胀脚本。
- 仅格式、注释或尚未落库的字段调整不得新增补丁。

## 4. 脚本头和注释

每个主版本必须在文件开头包含：

```sql
-- 业务域: exchange
-- 主版本: V0100
-- 脚本类型: MAIN
-- 变更说明: ...
-- 需求依据: ...
-- 数据边界: ...
-- 时间口径: ...
-- 回退方案: ...
```

补丁还必须包含：

```sql
-- 归属主版本: V0100
-- 补丁序号: 001
```

注释要求：

- 每个表必须在`CREATE TABLE`前说明表用途和不承担的职责。
- 每个字段必须说明业务含义、单位、时间口径、允许为空的条件或敏感数据边界。
- 每个主键、唯一约束、检查约束和外键必须说明保障的规则。
- 每个索引必须说明对应的真实查询或约束场景。
- `datetime2(3)`字段必须说明保存UTC还是医院本地时间；本项目默认保存UTC。
- 不得使用“备用字段”“扩展字段1”“状态”等含义不完整的说明。

### 4.1 SQL Server 元数据注释（强制）

- 源码中的`--`注释只用于代码评审，不能替代数据库元数据。所有正式表和字段必须写入名为`MS_Description`的 SQL Server 扩展属性，使 SSMS、数据字典和元数据查询能够直接查看中文说明。
- 主键、唯一约束、检查约束、外键、默认约束和显式创建的索引也必须写入`MS_Description`。新增约束必须显式命名，禁止依赖 SQL Server 自动生成名称。
- 表说明必须写在`SCHEMA/TABLE`层级；字段、约束和索引说明必须写在`SCHEMA/TABLE/COLUMN|CONSTRAINT|INDEX`层级。平台业务表默认使用`dbo`架构，非`dbo`架构必须在需求或工程决策中说明。
- 表和字段的扩展属性只保存简洁、明确的中文名称，不拼接业务长说明。表中文名称必须以“表”结尾，字段必须使用业务人员可理解的中文名称；不得包含英文对象名、技术类型或“见代码”等无效内容。
- 详细业务含义保留在迁移脚本源码注释中。时间字段的源码注释必须说明时间口径和精度；允许为空的字段必须说明为空条件；敏感字段必须说明保存形态或禁止保存边界。
- 新建对象的主版本必须同时创建对象和扩展属性。正式数据库基线评审前发现缺失或错误，必须收敛回主版本并重建开发库；只有正式基线后的历史对象才允许通过归属原主版本的补丁修正。
- 迁移脚本必须以可静态核对的对象说明清单声明扩展属性，清单格式统一为`(N'<TABLE|COLUMN|CONSTRAINT|INDEX>', N'<表名>', N'<对象名或NULL>', N'<中文名称或准确说明>')`。表和字段填简洁中文名称，约束和索引填准确作用说明；门禁按建表对象逐项核对，不接受仅有行内注释的脚本。
- 时间字段的`MS_Description`必须写明 UTC 或医院本地时间；敏感字段必须写明保存形态或禁止保存的边界。

## 5. 建模与兼容性

- 只建立已确认业务所需对象，字段类型、长度、空值、唯一性和默认值必须有需求或样例依据。
- 数据库对象使用`snake_case`；业务表由一个模块负责写入。
- 禁止无理由使用`nvarchar(max)`、`SELECT *`、无边界更新和删除。
- 不使用 SQL Server 2012 SP4 之后才提供的语法、函数和索引能力。
- 时间点使用`datetime2(3)`并明确口径；金额和计量值使用已确认精度的`decimal(p,s)`。
- 完整XML、JSON、病历、报告、密码、Token和验证码不得因排障方便直接进入普通业务表或日志表。
- 约束和索引名称在业务域内稳定、可读，不依赖SQL Server自动生成名称。

## 6. 检查与验证

本地和CI首先执行静态门禁：

```bash
node tools/verify-sql-migrations.mjs
```

静态门禁至少检查：

- 文件命名、全局版本唯一性及业务主版本唯一性；
- 补丁归属、序号连续性和每个主版本最多5个补丁；
- 必需脚本头、表用途、字段/约束说明和索引用途；
- 每个表、字段、主键、唯一约束、检查约束、外键、默认约束和显式索引均有可落库的`MS_Description`说明清单，且脚本实际调用`sys.sp_addextendedproperty`或`sys.sp_updateextendedproperty`；
- 禁止`SELECT *`和`nvarchar(max)`。

真实数据库验证必须另行在 SQL Server 2012 SP4、兼容级别110执行，覆盖空库迁移、已有版本升级、约束、索引、事务、锁、时间精度、失败回滚以及备份恢复。未执行真实数据库验证时，交付说明必须明确写“仅通过静态检查，尚未验证SQL Server”。

## 7. 评审清单

- [ ] 当前业务是否只有一个主版本？
- [ ] 主版本未进入共享环境时，补丁是否已合并回主版本？
- [ ] 补丁是否引用正确主版本、连续编号且未超过数量上限？
- [ ] 表、字段、约束、索引、时间和数据边界是否都有准确说明？
- [ ] 表、字段、关键约束和显式索引是否均已写入`MS_Description`，并能通过SQL Server元数据查询查看？
- [ ] 是否删除了未经需求确认的预留对象和字段？
- [ ] 是否通过静态门禁，并如实说明SQL Server真实验证状态？
