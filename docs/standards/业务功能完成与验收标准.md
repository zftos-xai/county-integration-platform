# 业务功能完成与验收标准

版本：1.0
生效日期：2026-09-18

本文仅规定业务功能开发计划、实施顺序和业务验收条件，不包含工程整理、部署、安全环境和内部管理事项。

## 1. 第一优先：确认首批业务范围

### 目标

确定首批真正需要开发的接口，避免同时铺开全部接口。

### 需要业务方确认

- 首批业务功能及实施顺序。
- 每项业务的发起方、接收方和使用人。
- 实际业务触发页面、按钮和时点。
- 成功、失败、重复和结果未知分别如何判断。
- 接口数量、交易码和成功码冲突。
- 患者、机构和业务单据如何关联。
- 每项业务的验收负责人。

### 建议首批范围

1. 机构、科室、人员等基础数据。
2. 健康档案查询或上传。
3. 健康体检查询或上传。
4. 一个资料完整的 PACS、LIS 或心电接口。

### 完成标准

每项首批业务都有明确的输入、处理步骤、输出、异常处理和验收负责人。

## 2. 第二优先：完成基础数据业务

按以下顺序开发：

1. 机构数据。
2. 科室数据。
3. 人员数据。
4. 药品目录。
5. 公共字典。
6. 其他已确认的基础数据。

每类数据必须完成：

- 从负责维护该数据的系统取得数据。
- 检查必填字段、代码和更新时间。
- 新增和更新平台数据。
- 正确处理停用数据。
- 记录失败原因。
- 支持县医院 HIS 只读查询。
- 核对来源数量、平台数量和 HIS 读取数量。

### 完成标准

业务人员能够说明数据来自哪里、平台保存了什么、HIS 能读到什么，以及错误如何处理。

## 3. 第三优先：检查检验业务

按业务量和资料完整程度依次接入：

1. PACS 影像检查。
2. LIS 检验。
3. 心电。
4. 检查检验互认。

每类业务至少覆盖：

- 申请单创建。
- 申请单撤销或变更。
- 报告查询。
- 报告回写。
- 报告版本变化。
- 目标系统不可用。
- 已发送但结果未知。
- 重复请求不会产生重复结果。

### 完成标准

申请单和报告能够按患者、就诊和业务单号正确关联，业务人员能够确认最终结果。

## 4. 第四优先：健康档案和健康体检

优先完成最主要的居民健康业务。

### 4.1 健康档案

- 查询健康档案。
- 上传健康档案。
- 修改健康档案。
- 处理重复居民和身份不一致。
- 查询目标系统最终处理结果。

### 4.2 健康体检

- 查询体检记录。
- 上传体检结果。
- 修改体检结果。
- 确认体检主记录与明细的关联方式。
- 处理重复上传、部分失败和结果未知。

### 完成标准

从 HIS 实际业务操作开始，到目标系统确认接收结果，整个业务过程可以复核。

## 5. 第五优先：电子病历业务

先确认 400-003 是否需要回写，再按确认结果开发。

建议顺序：

1. 病历查询。
2. 病历保存。
3. 历史病历调阅。
4. 病历回写。
5. 版本变化和重复保存处理。
6. 无权限和患者不匹配处理。

### 完成标准

病历读取、保存和回写责任清楚，不会把其他患者或其他就诊的病历关联到当前业务。

## 6. 第六优先：双向转诊和协同业务

完成基础医疗业务后再实施：

- 转诊申请。
- 转诊接收。
- 接收结果查询。
- 转诊撤回或失败处理。
- 患者档案摘要查询。
- 县医院端和基层端的状态展示。

必须明确：

- 谁发起。
- 谁接收。
- 哪个状态表示等待处理。
- 哪个状态表示已经接收。
- 失败后由谁处理。
- 两端页面分别展示什么。

### 完成标准

一笔转诊能够从发起、接收、处理到结果确认完整执行。

## 7. 每项业务的统一完成条件

一项业务只有同时满足以下条件才算完成：

- 真实业务入口已经接入。
- 请求字段和返回字段经过业务确认。
- 正常流程可以完成。
- 重复提交不会产生重复业务记录。
- 超时后不会直接再次提交。
- 可以查询目标系统最终结果。
- 失败原因对业务人员可理解。
- 患者、机构和业务单据关联正确。
- 业务负责人已经确认实际结果。

## 8. 总体实施顺序

基础数据 → PACS、LIS、心电 → 健康档案与体检 → 电子病历 → 双向转诊与协同业务。
