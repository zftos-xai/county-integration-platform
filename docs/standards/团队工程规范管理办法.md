# 团队工程规范管理与跨项目推广办法

本文规定工程规范如何维护、执行、审计和推广。具体技术规则仍以项目内的工程、前端、Java 和 SQL 专项规范为准；本文解决“由谁维护、何时执行、如何例外、怎样复制到其他项目”的问题。

## 1. 规则分层

团队规则分为三层，采用方不得把项目特有约束直接冒充通用标准。

| 层级 | 适用范围 | 典型内容 | 维护位置 |
| --- | --- | --- | --- |
| L1 团队底线 | 所有代码仓库 | 安全、秘密信息、评审、测试、可追溯性、完成定义 | 本文与团队插件 |
| L2 技术栈规范 | 使用对应技术的项目 | Vue/TypeScript、Java/MyBatis、SQL Server 规则 | 专项规范与插件参考资料 |
| L3 项目覆盖项 | 单一项目 | 包名、端口、数据库版本、业务术语、目录裁剪 | 项目 `AGENTS.md` 与项目规范 |

冲突时遵循“法律与安全要求 > 仓库 `AGENTS.md` > 项目规范 > 团队插件建议 > 工具默认值”。L3 可以收紧 L1/L2，不得静默放宽安全、兼容性和验证底线。

规范用语统一如下：

- **必须**：合并前检查或评审必须阻止不符合要求的代码合并。
- **应该**：默认执行；偏离时必须在变更说明中给出理由。
- **可以**：按项目成本和收益选择。

## 2. 最低执行要求

每个采用规范的项目必须具备：

1. 根目录 `AGENTS.md`，声明项目边界、技术选型和版本、专项规范入口和禁止事项。
2. 根目录 `.editorconfig`，统一字符集、换行、缩进和文件末尾换行。
3. `docs/standards/` 下的适用技术栈规范；不适用的技术栈不创建空文档占位。
4. 一个开发者可本地执行的统一验证入口，例如 `tools/verify.sh`、`npm run verify` 或 `make verify`。
5. CI 调用与本地相同的验证命令，至少覆盖编译、静态检查和自动测试。
6. README 明确开发环境、验证命令、敏感配置注入方式和当前实现边界。
7. 高风险变更保存可追溯证据；Web UI 验收使用项目认可的截图、页面区域清单和定向复验说明。

## 3. 规范变更流程

规范变更与业务代码一样通过分支、评审和 CI：

1. 说明问题、适用范围、现有风险和拟采用级别。
2. 同时更新文字规则、自动强制检查和正反例；无法自动化的规则必须明确人工评审点。
3. 对存量代码先进行只读盘点，区分“新增即执行”和“限期清理”，禁止一次性无边界格式化。
4. 至少由一名对应技术栈维护者评审；涉及安全、数据或兼容性时增加相应负责人。
5. 合并后在试点项目运行一个迭代，再推广到其他项目。

规则变更遵循按变更影响编号的版本：破坏现有采用方式为主版本，新增兼容规则为次版本，澄清和缺陷修正为补丁版本。插件版本与发布说明必须同步。

## 4. 例外管理

例外必须显式、限时、可追踪，至少记录：规则编号、影响文件、原因、风险、失败后补救措施、负责人和失效日期。以下内容不得以普通工程例外放宽：

- 凭证、患者信息或其他敏感数据进入源码、日志、测试样例和构建产物；
- 未验证却声称已验证，或用原型数据冒充真实结果；
- 绕过权限、审计、数据库兼容级别或已批准的已批准的安全要求；
- 删除、覆盖共享数据而没有明确授权与可恢复方案。

例外到期后 CI 或评审必须重新停止合并；永久差异应升级为项目覆盖项或正式修改规范，不能无限续期。

## 5. 自动化与证据

规范条款应优先映射为确定性强制检查：编译器、类型检查、单元测试、静态脚本、迁移校验和 UI 验收。CI 只接受可重复命令，不接受“本机看起来正常”作为证据。

本项目统一入口为：

```bash
./tools/verify.sh
```

前端强制检查单独执行：

```bash
npm run verify:frontend
```

团队插件自带的仓库仓库规则检查只判断必要规则是否存在，不替代项目自身测试：

```bash
python3 plugins/team-engineering-standards/skills/project-engineering-guardrails/scripts/audit_repository.py . --strict
```

## 6. 跨项目推广

推广时按以下顺序执行：

1. 识别项目技术栈、法规要求和既有约束，选择适用的 L2 规则。
2. 复制最低要求，不复制本项目专属包名、端口、业务词汇或数据库结论。
3. 运行插件审计并记录未满足的要求。
4. 先接入不改变业务行为的强制检查，再分批修正存量问题。
5. 将统一验证接入受保护分支的必需检查。
6. 在一个真实变更中验证规范、CI 和评审流程，然后再扩大范围。

仓库内的 `team-engineering-standards` 插件是团队分发载体。安装与更新方法见插件 README；项目即使不使用 Codex，也必须保留 Markdown 规范和 CI 强制检查，不能让制度依赖单一工具。

## 7. 责任分工与度量

- 规范负责人：维护层级、版本、例外和发布说明。
- 技术栈负责人：维护专项规则、自动化检查和迁移建议。
- 项目负责人：选择适用规则、配置必需检查并关闭到期例外。
- 开发者：在提交前运行统一验证，提交真实验证结果。
- 评审者：检查需求、权限、数据、兼容性、测试和实际差异，而非只看格式。

团队按月关注强制检查覆盖率、CI 失败原因、重复缺陷、例外数量与平均关闭时间。不得用代码行数、注释数量或 AI 生成量评价质量。

## 8. 技能与插件管理

技能负责向开发代理提供工作方法，插件负责版本化分发技能、工具或外部服务接入程序；二者都不能替代仓库规范、CI 和人工责任。团队采用时必须遵守：

- 跨项目必需的规则和工具放入仓库或团队 Marketplace，并使用按变更影响编号的版本；个人目录中的技能只能作为可选辅助。
- 引入第三方插件前审查来源、许可证、网络访问、数据范围、写入权限、认证方式和更新机制。
- 涉及生产数据、患者数据、凭证或外部系统写入的插件默认禁用，必须经过项目与安全负责人批准。
- 插件升级先在样板仓库验证，再在一个真实项目试点；不得自动扩大权限。
- 项目必须记录插件名称、来源、用途、是否必需和维护责任人，移除不用的外部服务接入程序和过期技能。
- 技能输出必须经过需求、权限、数据安全、兼容性、测试和实际差异检查，不得把代理报告当作验收证据本身。

当前工具清单：

| 名称 | 类型 | 用途 | 分发与约束 |
| --- | --- | --- | --- |
| `team-engineering-standards` | 仓库插件 | 规范检查、维护与跨项目推广 | 由本仓库 Marketplace 版本化分发，不访问外部业务数据 |
| `project-engineering-guardrails` | 插件内技能 | 规则分层、仓库规则检查、CI 强制检查实施 | 随上述插件分发；审计结果不能替代项目测试 |
| `vista-web-acceptance` | 专项技能 | Web 页面区域盘点、风险检查、修复和复验 | UI 任务按项目接入说明使用；团队环境需单独提供并锁定版本 |
| `unified-computer-use` | 环境插件 | 浏览器和桌面 UI 操作 | 仅在交互式验收需要时启用，不属于应用运行依赖 |

其他项目若没有 `vista-web-acceptance` 或浏览器控制插件，应使用等价的可追溯 UI 验收流程，不得因此取消 UI 验收。
