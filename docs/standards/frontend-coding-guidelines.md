# 前端工程与 AI Coding 规范（项目执行版）

本规范适用于本项目所有浏览器端工程，包括管理端、嵌入端、原型页面、前端测试、构建配置及由 AI 辅助产生的前端修改。规范以 TypeScript、Vue 3、Vue Router 和 Vite 为当前技术基线，同时将组件边界、状态管理、安全、可访问性、测试和交付要求写成可复用规则。

AI 生成内容只能作为待评审的工程修改。提交者对需求理解、交互正确性、权限边界、数据安全、兼容性、测试和实际差异承担责任。原型可用于确认流程和视觉，不得被当作真实接口、真实权限或联调成功的证据。

## 1. 规范优先级与基本原则

- 按“用户明确要求 > 已确认需求和接口合同 > 安全与数据要求 > 项目工程决策 > 本规范 > 框架惯例”的顺序处理冲突，并在交付说明中指出实质冲突。
- 修改前必须阅读相关路由、页面、组件、API 客户端、类型、样式和测试，不根据截图、组件名或模拟数据猜测业务规则。
- 只修改当前任务需要的内容；不顺带升级框架、替换组件库、重构全局样式、重排目录或格式化无关文件。
- 页面必须显式处理加载、空数据、成功、业务失败、无权限、会话失效、冲突、网络失败和后端不可用等适用状态。
- 浏览器端不可信。前端的路由守卫、按钮隐藏和表单校验只改善体验，不能替代服务端认证、授权、机构范围、幂等和数据校验。
- 不编造 API、字段、枚举、权限代码、机构范围、患者规则、环境地址、联调结论或性能数据。
- 信息不完整时使用安全状态：不提交不确定写入、不扩大权限、不展示敏感内容，并明确标记待确认项。

## 2. AI Coding 工作流程

### 2.1 开发前

开始编码前必须确认：

1. 用户目标、入口、主流程、异常流程和完成条件。
2. 页面属于正式功能、嵌入功能还是合成原型，三者的数据和认证状态不得混用。
3. API 路径、方法、请求/响应类型、错误码、并发版本及 OpenAPI 来源。
4. 登录状态、功能权限、机构数据范围和敏感字段展示规则。
5. 目标浏览器、响应式范围、键盘操作和可访问性要求。
6. 可执行的类型检查、测试、构建及真实环境验证方式。

不得为了通过演示或测试而硬编码账号、令牌、成功结果、权限、机构数据或患者信息，也不得关闭证书校验、CSRF、防重或错误处理。

### 2.2 实现中

- 优先复用已有布局、组件、API 客户端、状态词汇和样式变量，避免同一概念出现多套实现。
- 先确定数据与状态边界，再写模板；复杂页面应拆分数据访问、状态编排和纯展示职责。
- 修改 API 合同时同步检查调用方、类型、错误态、OpenAPI 和测试，不用 `any` 暂时掩盖不一致。
- 每次写操作都检查重复点击、处理中禁用、成功反馈、失败恢复、会话失效和并发冲突。
- 不用占位实现伪装成功。功能未接入时应明确显示“尚未接入”或“当前不可用”。
- 不引入未经说明的框架、状态库、UI 库、CSS 体系、代码生成器或运行时依赖。

### 2.3 交付前

- 检查实际差异，移除调试输出、临时账号、截图数据、无效注释、未使用样式和依赖。
- 至少运行受影响工程的 TypeScript 检查和生产构建；行为修改还必须运行相应自动化测试。
- 对关键流程执行浏览器验证，检查目标尺寸、键盘操作、控制台、网络请求和主要错误状态。
- 报告修改内容、验证命令、实际结果及尚需真实后端、真实浏览器或业务人员确认的限制。
- 没有证据时不得声称“已联调”“完全兼容”“可上线”或“无障碍通过”。

## 3. 工程结构与依赖方向

前端工程默认使用以下职责结构，目录仅在有实际内容时创建：

```text
src/
|-- api/              HTTP 客户端和按业务域划分的 API 调用
|-- assets/           随构建发布的静态资源
|-- components/       可复用、边界明确的展示或交互组件
|-- layout/           页面框架、导航和公共布局
|-- router/           路由定义、元数据和路由守卫
|-- store/            确需跨路由共享且生命周期明确的全局状态
|-- utils/            有具体技术职责的纯函数和基础设施工具
|-- views/            按 views/<领域>/<业务>组织页面、表单模型和局部组件
|-- App.vue           根组件
`-- main.ts           应用装配入口
```

- `main.ts`只负责创建应用、注册路由和全局能力，不放业务请求或页面状态。
- `views`负责路由级用例编排，业务页面、表单模型和仅供该业务使用的组件按领域就近放置；跨业务复用的复杂控件才提取到顶层 `components`。
- `components`不得直接依赖具体路由参数，除非组件本身就是导航组件；可复用组件通过明确的 props、events 和 slots 协作。
- `api`只负责协议、序列化、响应解析和错误转换，不操作 DOM、路由或页面提示。
- `store`只保存确需跨路由共享且有明确失效条件的状态，不把页面表单和服务端列表全部全局化。
- 通用工具只允许纯函数和明确技术职责。禁止创建无边界的 `helpers.ts`、`common.ts`、`misc.ts`；现有 `utils` 中新增文件必须使用具体名称，业务规则应放在对应业务模块。
- 不再把业务页面、表单模型和业务规则堆到 `src` 根目录，也不另建 `features` 形成第二套组织方式；同一业务域不得形成两套 API、类型或状态来源。
- 依赖方向通常为 `view -> component/store -> api`；API 和基础组件不得反向依赖具体页面。
- 跨顶层模块导入统一使用 `@/` 指向当前工程的 `src`，例如 `@/api/system/user`；相对路径只用于同一业务目录内的相邻文件。禁止用 `../../`、`../../../` 等深层相对路径穿越模块边界。
- 管理端与嵌入端不得相互引用源码目录。确需共享时，应先确认稳定边界，再建立独立、受测试的共享包，不用复制粘贴维持两份逻辑。

## 4. TypeScript 与命名

- 所有正式源码必须通过 `strict` TypeScript 检查；禁止用 `any`、`@ts-ignore`、双重类型断言或关闭严格选项掩盖问题。
- 外部输入初始类型应视为 `unknown`，在边界完成校验和收窄后再进入业务代码。
- API 请求、响应、表单状态和领域对象使用不同类型表达；不得直接修改 API 返回对象作为未提交表单草稿。
- 优先使用联合类型、判别联合和只读结构表达有限状态；不使用多个可能互相矛盾的布尔值表示同一流程。
- Vue 组件文件使用 PascalCase；组合函数使用 `useXxx`；普通函数和变量使用 camelCase；常量使用 `UPPER_SNAKE_CASE`。
- 事件名称表达已发生的动作，如 `saved`、`selectionChanged`；回调函数使用 `handleXxx`，实际业务动作使用动词，如 `loadOrganizations`、`disableUser`。
- 布尔值使用 `is`、`has`、`can`、`should` 开头；集合使用复数；时间名称包含准确语义和 `At` 后缀。
- 禁止无语义的 `data`、`info`、`item1`、`temp`、`handleData` 以及不统一的拼音或缩写。
- 类型、接口、props 和 emits 只描述真实合同。不要为了“以后可能用到”加入可选字段。
- 对浏览器定时器、事件、Observer 和网络取消句柄使用准确类型，并在组件卸载时释放。

## 5. Vue 组件规范

- 新组件默认使用 Composition API、`<script setup lang="ts">` 和类型化 props/emits；同一工程不混用多种组件风格。
- 组件保持单一主要职责。模板出现多段独立业务流程、重复交互区或难以命名的大量状态时应拆分。
- props 视为只读，不在子组件直接修改；需要双向编辑时使用明确的 `modelValue`/`update:modelValue` 或表单草稿。
- `computed`用于派生状态且不得产生副作用；副作用放在明确的事件函数、生命周期或必要的 `watch` 中。
- `watch`必须说明触发目的并限制依赖范围；不得用深度监听代替清晰的数据流。
- 列表必须使用稳定业务标识作为 `key`，不得在可增删或重排列表中使用数组下标。
- 模板不得包含复杂业务表达式；提取为有名称的 `computed` 或函数。
- DOM 引用只用于框架无法声明表达的行为，并处理引用为空和组件卸载。
- 组件暴露的 props、events、slots、错误状态和可访问性语义发生变化时，必须同步调用方和测试。
- 所有导出的 TypeScript 类型、接口、类、常量和函数必须在声明前使用准确 TSDoc 说明职责或合同；每个 Vue 单文件组件必须在文件顶部使用 HTML 注释说明页面或组件职责。
- 权限、会话、并发控制、敏感数据和兼容性等非显然逻辑必须解释“为什么”，不得逐行翻译实现。普通未导出的局部函数不强制机械注释，但复杂业务分支仍应说明原因。

## 6. 状态、表单与异步流程

- 状态按作用域存放：组件局部状态留在组件；跨同一用例复用的状态进入组合函数；只有跨路由共享且有明确生命周期的状态才进入全局状态。
- 服务端数据以服务端为准。不得通过本地存储长期维护另一份可写业务真相。
- `localStorage`和`sessionStorage`不得保存密码、Token、Session 标识、患者正文、完整身份信息或可恢复敏感数据。
- 每个异步动作必须防止重复提交，并在 `finally` 或等效路径恢复 loading 状态。
- 对可能乱序完成的搜索、筛选和详情请求使用取消、请求序号或结果归属检查，防止旧响应覆盖新状态。
- 表单分别维护原始数据、编辑草稿、校验错误和提交状态；取消编辑不得污染列表中的已保存对象。
- 前端校验用于即时反馈，后端错误仍须按字段错误、业务拒绝、冲突或系统失败正确展示。
- 时间输入、时区、空值和格式转换必须明确，不依赖浏览器隐式解析非标准日期字符串。
- 成功提示只在服务端确认成功后出现；网络超时或连接中断不能推断写入失败，按后端幂等和查询合同处理结果未知。
- 页面卸载后不得继续更新已失效状态；长请求适用时使用 `AbortController`。

## 7. API、认证、权限与错误处理

- HTTP 请求统一经过项目 API 客户端，统一处理基础路径、同源凭据、CSRF、超时、响应结构、`requestId`和受控错误；组件不得散落原始 `fetch`。
- API 函数按业务动作命名并返回已解析的明确类型；页面不重复解析统一响应包装。
- 路径、方法、字段、状态码和错误码必须来自稳定 OpenAPI 或已确认合同；合同变化同步更新类型、调用方和测试。
- 401表示会话失效时进入统一重新登录流程；403显示无权限，不得伪装为404或自动扩大权限；409保留用户输入并提供刷新或重试路径。
- 路由元数据和按钮可按后端返回的权限代码控制显示，但服务端必须再次授权。前端不得自行推导额外机构范围或角色能力。
- 切换用户、改密、权限或机构范围变化时，应清理旧主体状态并重新获取权限，避免沿用过期会话视图。
- 错误提示面向用户说明可采取的下一步；存在 `requestId` 时显示以便定位，但不得展示堆栈、SQL、内部地址或敏感响应。
- 不在 URL、日志、埋点、错误文本或浏览器存储中放置密码、Token、Cookie、凭证引用、患者正文和未脱敏身份数据。
- 禁止把 Vite 的 `VITE_*` 变量当作秘密；所有进入前端构建的环境变量均视为公开信息。
- 外链、下载和新窗口操作必须验证来源及文件类型，并按风险使用 `noopener`、受控文件名和明确用户动作。

## 8. 路由、页面状态与原型隔离

- 每个路由必须定义稳定路径、页面标题、是否公开、所需权限和布局；未知路由进入受控404页面。
- 路由守卫不得只依赖菜单是否可见；首次进入和刷新页面都必须恢复并验证当前主体。
- 页面至少考虑首次加载、局部刷新、无数据、无筛选结果、无权限、会话过期、后端不可用和请求失败。
- 会导致未保存内容丢失的路由离开、关闭抽屉或切换对象，应提供确认或明确保存状态。
- `/prototype`等合成原型必须与正式登录、Session、API 状态和本地业务数据隔离；原型账号和模拟数据不得出现在正式入口。
- 从原型转为正式页面时，必须删除或隔离合成保存逻辑，并记录真实 API 尚未覆盖的差异。
- 嵌入页面应限制能力和展示范围，不提供管理端导航，不通过 URL 传递长期凭证或患者敏感信息。

## 9. HTML、样式、响应式与可访问性

- 优先使用语义化 HTML。按钮使用 `button`，导航使用链接，表单控件关联可见 `label`；不得用 `div`模拟可点击控件。
- 所有交互必须支持键盘操作并具有可见焦点；弹窗、抽屉和菜单应管理焦点进入、循环、退出及 `Escape`行为。
- 图标按钮必须提供可访问名称；装饰图标不重复朗读；状态不能只依赖颜色表达。
- 动态成功、错误和加载状态按影响使用 `role="status"`、`aria-live`或 `role="alert"`，避免无意义的高频播报。
- 文本和关键控件必须具备足够对比度；页面缩放到200%时核心流程仍可使用。
- 使用项目级 CSS 变量表达颜色、间距、圆角、字体和层级；禁止在不同页面复制近似但不一致的设计值。
- 组件样式默认限定作用域；真正跨页面的基础样式放入 `styles` 并使用明确层级。不得使用无边界的全局选择器覆盖第三方组件内部结构。
- 响应式布局优先使用 Flexbox、Grid、`minmax`、相对单位和内容驱动断点，不为单台设备硬编码像素位置。
- 不用 `!important`解决层叠设计问题，确需使用时应有具体原因且范围最小。
- 动画应简短、可中断，并尊重 `prefers-reduced-motion`；不得让动画阻塞业务操作。
- 图片必须提供合适替代文本、明确尺寸并避免不必要的大文件；图标优先复用现有图标系统。

## 10. 性能与浏览器兼容

- 性能优化必须基于实际页面和构建证据，不为假设问题引入复杂缓存或状态库。
- 路由级大页面适用时进行懒加载；首屏必要代码不得被无关管理功能拖大。
- 大列表使用服务端分页或明确上限，不一次加载无边界数据；高频输入使用合理防抖并保留立即反馈。
- 避免在模板渲染中重复排序、深拷贝或执行高复杂度计算；使用稳定派生状态。
- 不重复请求可复用的稳定元数据，但缓存必须定义失效条件，权限和机构范围变化后立即失效。
- 新浏览器 API 必须核对目标环境支持情况；需要兼容处理时使用小而明确的降级，不静默破坏核心流程。
- 构建产物不得包含 source map 中的秘密、测试数据或未使用的大型依赖。产物体积显著增长时说明原因。

## 11. 测试与验证

- 测试名称表达“条件—动作—预期”，测试用户可见行为和稳定合同，不绑定无关 DOM 结构或私有实现。
- 纯函数覆盖边界值、空值、非法值、时间和状态转换；API 客户端覆盖请求方法、路径、凭据、CSRF、错误码和 `requestId`。
- 组件和页面覆盖加载、空数据、成功、失败、401、403、409、重复提交和恢复路径中的适用场景。
- 权限测试必须同时覆盖菜单/按钮显示、直接 URL 访问和服务端拒绝；前端通过不能替代后端授权测试。
- 修复缺陷时增加能复现原问题的回归测试；不得删除、跳过或放宽断言来隐藏失败。
- 测试不得依赖执行顺序、公共环境残留数据、真实账号、生产数据或不受控网络。
- 合成测试数据必须明显为测试数据，不使用真实患者、真实凭证或可识别个人信息。
- 自动化测试不能替代浏览器验收。关键流程还应检查布局、焦点、键盘、响应式、控制台和网络请求。
- 前端交付至少执行：

```bash
node tools/verify-frontend-comments.mjs
npm run typecheck --workspace web-admin
npm run build --workspace web-admin
npm run typecheck --workspace web-embed
npm run build --workspace web-embed
```

存在独立测试命令或项目级验证脚本时必须同时执行；无法执行时说明具体原因，不能写成“默认通过”。

## 12. 依赖、配置与构建

- 新依赖必须说明必要性、许可证、维护状态、安全风险、包体积和与当前 Vue/TypeScript/Vite 版本的兼容性。
- 能用平台能力或现有依赖清晰完成的功能，不新增功能重叠的库。
- 不擅自升级框架、构建工具、组件库、TypeScript 或锁文件；依赖升级作为独立变更验证。
- 应提交锁文件并使用确定性安装；不得手工修改构建产物代替源码修改。
- 环境地址通过配置提供，业务代码不得按开发、测试、生产环境写分支逻辑。
- 公开配置应有类型、默认值、合法范围和错误提示；生产关键配置缺失时不得悄悄回落到演示地址。
- `dist`、覆盖率、临时截图、浏览器缓存和本地环境文件按仓库约定处理，不把生成物误作源码评审内容。
- 开发代理只服务本地开发，不改变生产同源、安全 Cookie、TLS 和反向代理边界。

- [ ] 实现符合已确认需求、接口合同、原型决策和工程边界。

## 14. 自动检查范围与后续门禁

当前 `tsconfig.json` 已启用严格 TypeScript 检查，`tools/verify-frontend-comments.mjs`检查导出 TypeScript 声明的 TSDoc 和 Vue 文件顶部职责注释，Vite 生产构建能够发现类型、模块和构建错误。现有测试覆盖部分 API 合同、路由权限、表单规则和原型流程。

静态检查不能证明需求正确、权限安全、视觉一致、无障碍合格或真实接口已联通。提交者和评审者仍须检查浏览器行为、网络请求、数据边界和实际差异。

注释门禁只能检查注释是否存在，不能判断内容是否准确；提交者和评审者仍须核对注释与真实职责和合同一致。后续可以独立引入 ESLint、Vue ESLint、格式化检查、组件测试和浏览器端到端测试，但必须先明确规则、修复存量问题并接入统一验证脚本；不得用大量禁用项或自动格式化无关文件让门禁名存实亡。
