# 项目规范执行与评审

本文件把质量判断前移到编码前。规范文字不是设计本身；本地检查、CI、独立评审和真实环境验证只为已确定的设计兜底。

## 变更的固定路径

1. 简单局部修复直接读相邻代码和测试；跨 Controller、Service、Mapper、权限、数据库或外部接口的变更，先画出真实调用链，写出拟保留、修改和新增的关键方法签名。设计结论可写在任务讨论中，不强制另建文档。
2. 在编码前回答三个问题：参数由谁提供、授权及机构范围在哪一层确定、失败或结果未知时调用方看到什么。新增 DTO/VO 或抽象必须有现有类型不能表达的语义；只有字段转抄时先删掉多余类型。
3. 用越权但有机构范围、无登录主体的内部调用、空机构范围、重复请求及结果未知等反例试设计。不能自然说明这些场景时，先改签名和边界，不开始填方法体。
4. 按已确定契约实现，并同步补对应的拒绝或失败路径测试。提交前运行 `./tools/verify.sh`；Windows 使用 `./tools/verify.ps1`。无法运行的 SQL Server 或厂商接口验证明确记为未验证。
5. PR 使用仓库模板对照编码前的设计决定说明实际差异。评审者先判断签名、对象必要性和边界，再看实现细节与验证。CI 的 `verify` 作业只负责可重复的兜底检查；发现重复缺陷时补测试或确定性检查。

## GitHub 合并保护配置

仓库管理员在这份工作流合并并首次成功运行后，为 `main` 启用保护：要求通过 PR 合并、要求最新提交的 `verify` 检查成功、禁止绕过必需检查。工作流检查名称应从实际首次运行中选择，不根据文件名猜测。保护启用后再以一个测试 PR 核实失败检查确实阻止合并。

`CODEOWNERS` 当前只指定已核实的仓库所有者 `@zftos-xai`，不能伪称已经具备独立技术评审。指定第二位真实维护者之前，不启用“必须由 Code Owner 批准”这一可能使单人仓库无法合并的选项。涉及身份、权限、医疗数据、SQL 兼容性或不可逆变更时，仍须按专项流程找到独立评审者；无人可评审时暂停该类变更，不以自我批准替代。

## 规范演进

规则变更遵守[团队工程规范管理办法](团队工程规范管理办法.md)：同一 PR 更新规范、自动检查与正反例；先盘点存量影响，再决定新增即执行或限期清理。自动检查只拦确定性问题，例如缺少入口权限声明、包布局、表名注释合同和迁移命名；方法是否易懂、对象是否多余、注释是否有业务价值由人评审。例外必须有影响范围、风险、补救措施、负责人和到期日。

本轮按上述设计重看三条只读列表：批次、医院目录、医疗目录。编码前确定的方法契约是 `findPage(query, allowedOrganizationCodes)`，因为这三个用例只需要机构范围，不需要用户ID或登录名；功能权限和显式机构筛选由HTTP入口检查，Mapper仍按给定机构集合限域。按ID读取和写操作保留操作人，因为读取对象后才知道归属机构，且写入还涉及审计。空机构范围时，目录查询无机构行，批次查询只保留平台级批次；这些反例由Web测试、Service测试和生成SQL测试覆盖。不新增新的查询上下文或VO。
