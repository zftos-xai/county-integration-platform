# 县人民医院与基层卫生院中间接口平台工程建设规范

> 文档版本：V0.1（内部评审稿）  
> 内部修订：20260916.1
> 编制日期：2026年9月16日
> 适用范围：中间接口平台、县人民医院HIS改造、管理端、嵌入页面、接口联调、私有化部署及交付  
> 建设关系：县人民医院 ⇄ 所辖基层卫生院

## 一、规范目的与适用原则

### 1.1 规范目的

本规范用于把[总体方案](../plans/总体方案.md)转化为可执行的工程要求，统一项目结构、命名、接口、数据库、配置、安全、测试、发布和交付方式。项目成员、配合厂商和运维人员应以本规范作为设计评审、代码检查、联调验收和上线移交的共同依据。

本规范不替代业务需求、正式接口文件或双方书面确认。遇到材料不一致时，按“已批准的项目范围、双方书面确认、正式接口文件、本规范、其他参考材料”的顺序执行，并在问题台账中保留处理结论。

### 1.2 项目边界

- 平台只服务于县人民医院与所辖基层卫生院之间的双向协同，不增加第三个业务层级。
- 平台负责统一接入、身份验证、数据检查、格式转换、状态反馈、失败处理、运行记录、对账和管理，不替代HIS、电子病历、LIS、PACS或基层业务系统办理诊疗业务。
- 平台保存经批准的基层基础数据；县医院HIS厂商在平台数据库上建立受控视图，县医院HIS使用独立只读账号读取。除该基础数据读取外，其他业务按`PHIS_Interface`等正式接口交互。
- 平台保存经批准的基层机构、人员、科室、目录等基础数据及接口运行、问题处理、追溯和审计所需的数据，不复制完整诊疗、病历、报告、影像或健康档案业务库。
- 基层卫生院之间不通过本平台进行横向数据共享；任何系统不得绕过统一接口直接访问另一方业务数据库。
- 现有75项业务能力是总体范围基线。接口启用范围、调用方向、字段、地址、权限或验收规则不明确时，一律列为P0事项，在第1至2周取得书面结论。

### 1.3 核心链路约束

完整链路及关系图统一见[总体方案](../plans/总体方案.md)，本规范只规定工程约束。

- 基础数据进入平台的具体传输方式必须以正式来源合同为准；县医院HIS固定使用独立只读账号查询平台库视图。
- 除基层基础数据读取外，其他业务必须通过正式接口交互，不得用视图绕过校验、权限、状态记录或审计。
- 接口、数据库、权限、测试和运维设计必须标明所属链路，不得用一条无方向的“双向连接”代替。

### 1.4 规范用语

| 用语 | 执行含义 |
|---|---|
| 必须 / 不得 | 强制要求，不满足不得合并代码、进入联调或发布上线 |
| 应 | 原则上必须执行；确需偏离时，应记录原因、影响和批准人 |
| 可以 | 可选做法，不作为验收的强制条件 |
| P0事项 | 会影响范围、接口实现、数据安全或两个月完整交付的待确认事项 |
| 完成 | 已实现、已测试、已留存证据，并由规定责任人确认 |
| 接口条件不具备 | 缺少正式文件、脱敏样例、网络、凭证或责任人，暂不得开展具体适配 |

页面能够打开、接口单次返回成功或开发人员口头确认，均不能单独作为“完成”依据。

## 二、总体技术与工程原则

### 2.1 技术基线

| 层次 | 建设基线 | 主要约束 |
|---|---|---|
| 后台服务 | Java 17、Spring Boot 3.5、MyBatis | 建设一个可独立部署的单体应用，按业务能力划分模块 |
| 数据库 | Microsoft SQL Server 2012 SP4，兼容级别110，安装医院批准的最新可用安全/GDR更新 | 使用独立平台数据库和独立账号，不在HIS业务库内建平台表；上线前记录版本、补丁和风险接受结论 |
| 管理端 | Vue 3、TypeScript | 用于机构、接口、映射、交换记录、异常、告警和配置管理 |
| 嵌入页面 | Vue页面或网页组件 | 适配HIS及基层工作站浏览器环境，服务端进行最终权限判断 |
| 接口合同 | OpenAPI 3.x、正式接口说明及字段映射表 | 合同、实现、测试和交付文档保持一致 |
| 数据库变更 | 版本化SQL脚本 | 测试和生产执行同一份脚本，不允许人工直接改表 |
| 构建交付 | Maven、Node.js、版本化安装包 | 测试和生产使用同一批次、可校验的交付制品 |

Spring Boot 4不作为首期默认版本。待相关组件、应用服务器和医院运行环境完成兼容验证后，可通过正式升级评审另行实施，不在开发过程中直接更换主版本。

### 2.2 建设原则

1. **单体部署、模块分明**：一个后台应用统一部署，代码按业务能力分包，禁止所有逻辑堆积在控制器或通用工具类中。
2. **接口确认后开发**：没有正式字段、样例、调用规则和责任人的接口，不猜字段、不做替代实现、不宣称联调完成。
3. **来源可以追查**：每笔交换记录能够定位到机构、源系统、源业务单号、接口、处理时间、处理结果和错误原因。
4. **重复调用结果可控**：网络重试、用户重复提交或服务重启不得造成重复收费、重复登记或重复写入。
5. **权限默认收紧**：用户、系统和基层机构只能访问完成授权的数据；前端隐藏按钮不等于完成权限控制。
6. **环境相互隔离**：开发、测试、联调和生产配置分开，生产数据和凭证不得复制到普通开发环境。
7. **交付以证据为准**：代码、配置、数据库脚本、测试记录、部署记录和验收结果必须能够相互对应。

### 2.3 重要决策记录

出现以下情况时，应在`docs/decisions/架构决策.md`中追加编号决策：更换核心技术版本、改变数据库或部署方式、新增或改变供HIS读取的平台库视图、增加对外访问入口、改变患者匹配规则、引入新的基础组件、实施不可直接回退的数据库变更。记录至少包括背景、决定、影响、风险、恢复方法和批准人。

## 三、工程结构与职责边界

### 3.1 建议仓库结构

```text
county-integration-platform/
|-- backend/                         Spring Boot后台应用
|   |-- pom.xml
|   `-- src/
|       |-- main/java/cn/zqkj/platform/
|       |   |-- PlatformApplication.java   应用启动入口
|       |   |-- common/                    统一响应和异常等明确公共类型
|       |   |-- framework/                 Spring、安全和Web技术装配
|       |   |-- system/                    机构、身份、权限和平台配置管理
|       |   `-- exchange/                  接口交换和运行追踪
|       |-- main/resources/
|       |   |-- mapper/<业务域>/      MyBatis XML
|       |   |-- db/migration/        SQL Server变更脚本
|       |   `-- application.yml      非敏感默认配置
|       `-- test/                    镜像主代码包结构的测试
|-- web-admin/                       管理端
|-- web-embed/                       嵌入页面或组件
|-- contracts/                       OpenAPI、字段映射和脱敏样例
|-- deploy/                          私有化部署、备份和运行手册
|-- docs/                            设计、决策、联调和验收资料
|-- tools/                           构建、检查和部署辅助脚本
`-- README.md
```

目录应在有实际内容时创建，不通过空目录或仅含`package-info.java`的包提前表示未来模块。不得使用`temp`、`misc`、`other`、`shared`、`utils`等边界不清的包。`common`只允许统一响应、异常等职责明确且不包含业务规则的类型；Spring和安全技术能力放入`framework`的明确子包。

### 3.2 后台模块内部结构

系统管理域和交换域按实际需要采用以下结构，不要求没有实际代码的目录提前创建：

```text
<业务域>/
|-- controller/       仅存放HTTP控制器
|-- domain/
|   |-- dto/          HTTP请求DTO和服务输入命令
|   |-- model/        内部业务及持久化模型
|   `-- vo/           API输出VO，类名使用VO后缀
|-- mapper/           仅存放MyBatis Mapper接口
`-- service/          业务服务接口
    `-- impl/         业务规则、用例编排和事务实现
```

- `controller`不得存放Request、DTO或VO，不得直接调用MyBatis Mapper，不得编写SQL或核心业务判断。
- `mapper`不得存放Repository接口、`MyBatis...Repository`实现或业务规则；Mapper XML统一放在`resources/mapper/<业务域>`。
- 常规依赖方向为`controller -> service接口 -> service.impl -> mapper`，`domain`保存各层共同使用且不依赖Spring、MyBatis或厂商SDK的业务类型。
- 一个数据库表只由一个业务模块负责写入；其他模块通过该模块的服务访问。
- 外部系统调用集中在对应业务域内职责明确的`client`子包中，不得散落在定时任务、页面控制器或工具类中。
- HIS、基层系统、LIS、PACS等厂商差异应由接口配置、字段映射或独立适配类处理，不得污染所有业务代码。
- 统一异常和响应格式放入`common`，安全上下文和追踪能力放入`framework`；具体业务状态不得放入这两个包。
- 业务域之间通过Service稳定边界协作，不得直接引用其他业务域的Mapper或访问其负责写入的表。

### 3.3 页面职责

- 管理端按`机构与权限、接口与映射、交换记录、异常与再次处理、对账、告警、审计`划分功能。
- 嵌入页面只提供约定的业务入口或结果查看，不长期保存患者敏感数据和访问凭证。
- 页面请求必须携带可校验的登录身份、机构和用途信息；服务端重新判断权限。
- 首次加载、处理中、成功、失败、空数据、无权限、目标系统不可用等状态必须有明确显示。

## 四、命名与代码规范

### 4.1 通用命名

| 对象 | 规范 | 示例 |
|---|---|---|
| Java基础包 | 全小写、组织域名倒序加简短项目名 | `cn.zqkj.platform` |
| Java类 | PascalCase，名称表达职责 | `ExchangeRecordService` |
| 方法和变量 | camelCase，使用动词或有意义名词 | `retryFailedExchange` |
| 常量 | 全大写，下划线分隔 | `MAX_RETRY_COUNT` |
| REST路径 | 小写、复数名词、短横线分隔 | `/api/v1/exchange-records` |
| JSON字段 | camelCase | `sourceRecordId` |
| 数据库对象 | 小写、下划线分隔 | `exchange_record` |
| Vue组件 | PascalCase | `ExchangeDetailDrawer.vue` |
| 前端组合函数 | `use`开头 | `useExchangeRecords.ts` |
| 配置键 | 小写、短横线层级 | `integration.retry.max-count` |

集合名称使用复数；布尔值以`is`、`has`、`can`或`should`开头；时间字段写清语义，如`businessOccurredAt`、`receivedAt`、`processedAt`。禁止使用`data1`、`temp2`、`obj`、`handleData`等无法判断含义的名称。

### 4.2 统一业务术语

| 中文含义 | 代码名称 |
|---|---|
| 机构 | `organization` |
| 基层卫生院 | `primaryHealthCenter` |
| 源系统 | `sourceSystem` |
| 患者 | `patient` |
| 源业务记录 | `sourceRecord` |
| 接口定义 | `interfaceDefinition` |
| 交换记录 | `exchangeRecord` |
| 交换批次 | `exchangeBatch` |
| 字段映射 | `fieldMapping` |
| 编码对应 | `codeMapping` |
| 数据核对事项 | `reconciliationTask` |
| 人工处理 | `manualHandling` |

同一概念不得在不同模块混用多组英文名称。接口文件确认的行业术语优先；新增术语应同步维护术语表。

### 4.3 Java与MyBatis约束

- Controller统一使用请求对象和响应对象，不直接暴露数据库实体。
- Service明确事务范围；外部HTTP调用不得长期占用数据库事务。
- MyBatis SQL必须参数化，禁止拼接用户输入；动态排序字段采用白名单。
- 查询必须限定必要字段，禁止生产代码无条件`SELECT *`。
- 列表查询必须分页；大批量处理采用分批读取，单批大小通过测试确认。
- 异常不得静默忽略。业务失败、外部系统失败、数据校验失败应使用不同错误类型和可理解的错误信息。
- 日期时间统一使用明确时区。平台记录时间以医院确定的统一时区保存和展示，对外接口按合同转换。
- 不在代码中固定机构编码、接口地址、账号、密钥、患者规则或厂商环境差异。

### 4.4 Git与评审

- 分支使用`feature/<编号>-<说明>`、`fix/<编号>-<说明>`、`docs/<编号>-<说明>`。
- 提交使用`feat:`、`fix:`、`docs:`、`test:`、`refactor:`、`chore:`前缀，一个提交围绕一个可评审目的。
- 核心接口、患者对应、权限、数据库和再次处理逻辑必须由另一名开发人员复核。
- 不得提交生产数据、账号密码、证书私钥、个人编辑器文件、临时导出和无法说明来源的二进制文件。

## 五、接口与数据规范

### 5.1 接口准入

每项接口进入开发前必须具备：

1. 正式接口说明和启用范围；
2. 调用方、提供方、业务负责人、技术负责人和验收负责人；
3. 测试地址、生产地址申请方式、网络路径和身份验证方式；
4. 请求字段、响应字段、值域、必填规则、时间和金额单位；
5. 真实脱敏样例及预期结果；
6. 超时、重复、失败、再次处理、撤销和查询规则；
7. 业务闭环场景和验收证据。

缺少关键条件时，接口台账状态标记为“接口条件不具备”，由项目对接人员纳入P0日跟踪，不得依据猜测开始厂商适配。

### 5.2 接口台账与状态

接口按“业务领域 + 调用方向 + 交易码或接口编号 + 版本”唯一登记。台账至少记录接口名称、双方系统、方向、是否启用、正式版本、负责人、环境、凭证状态、样例状态、开发状态、联调状态、验收结果和遗留问题。

统一状态为：`待确认`、`条件不具备`、`可开发`、`开发中`、`待联调`、`联调中`、`待验收`、`已通过`、`已停用`。状态变化必须记录时间、操作人和依据。

### 5.3 统一请求与响应信息

在不改变外部正式合同的前提下，平台内部每笔调用至少关联：

| 信息 | 用途 |
|---|---|
| `requestId` | 标识一次调用，便于查询日志 |
| `traceId` | 串联基层、平台和县医院的完整处理过程 |
| `interfaceCode`、`interfaceVersion` | 标识接口及其版本 |
| `sourceSystemCode`、`targetSystemCode` | 标识数据来源和去向 |
| `organizationCode` | 限定业务所属机构和权限范围 |
| `sourceRecordId` | 标识源业务记录 |
| `idempotencyKey` | 判断是否为同一笔重复请求 |
| `occurredAt`、`receivedAt` | 区分业务发生时间和平台接收时间 |
| `resultCode`、`resultMessage` | 返回稳定结果码和可理解说明 |

HTTP状态表示通信处理结果，业务结果由稳定的业务结果码表达。不得只返回“成功/失败”而不提供可定位的编号；不得把程序异常堆栈直接返回给页面或外部系统。

### 5.4 防重复、再次处理与对账

- 写入类接口必须定义防重复键及有效范围。同一防重复键重复到达时，应返回第一次的明确结果，不得再次执行有效写入。
- 对网络超时等“结果未知”情况，必须先查询目标系统或执行对账，不得直接重复提交。
- 自动再次处理只用于已确认可以安全重试的错误，并限制次数和间隔；超过限制转人工处理。
- 人工再次处理必须记录操作人、原因、原请求、前次结果和本次结果。
- 每项核心业务应具备按日期、机构、接口和业务单号对账的能力，能够区分未发送、发送失败、结果未知、双方不一致和已完成。

### 5.5 SQL Server规范

- 数据库版本统一为SQL Server 2012 SP4，兼容级别110；所有脚本、驱动、Flyway迁移、事务和锁行为必须在同版本测试实例验证。
- SQL Server 2012已结束常规扩展支持和扩展安全更新。上线前必须完成医院风险审批、补丁核对、网络隔离、备份恢复验证和后续升级计划。
- SQL Server 2012不使用Linux容器部署，由医院在Windows Server或现有SQL Server实例提供数据库服务。
- 平台使用独立数据库、独立账号、独立备份和维护计划；默认禁止平台账号修改HIS业务表。
- 平台数据库可与HIS数据库部署在同一台服务器或同一SQL Server实例，但平台库读写账号、HIS读取平台库视图的只读账号和视图DDL变更账号必须分离。
- 平台库视图必须有正式合同，明确消费方、最小字段、过滤范围、查询频率、单次上限、允许时段、版本兼容和性能基线；HIS运行账号只授予指定视图`SELECT`权限。
- 除读取基层基础数据外，业务查询和写入不得通过数据库视图绕过正式接口。
- 数据库对象使用`snake_case`。在独立平台库中按领域使用前缀，如`sys_`、`intf_`、`map_`、`exch_`、`recon_`、`audit_`。
- 内部主键优先使用`bigint identity`；跨系统业务编号单独建唯一约束，不以姓名、身份证号或手机号作为主键。
- 时间点使用`datetime2(3)`；金额和计量值使用明确精度的`decimal(p,s)`；文本长度按正式合同确定，禁止无理由全部使用`nvarchar(max)`。
- 需要并发更新的配置和任务表使用`rowversion`或等效校验，防止后提交的数据无提示覆盖先提交的数据。
- 索引以真实查询、对账和清理场景为依据；高频表必须包含机构、接口、状态、业务时间等常用查询条件的验证记录。
- 患者敏感字段按医院安全要求加密或信息隐藏；日志表不保存完整请求响应正文，确需留存的报文应受控保存并设置期限。
- SQL建设、主版本、补丁、注释和验证统一遵守[SQL Server建设与迁移脚本规范](sql-coding-guidelines.md)。一个业务域只能有一个主版本；未进入共享环境的修复必须收敛回主版本，不得用连续补丁掩盖未稳定设计。
- 已进入共享环境的主版本和补丁不得修改；后续补丁使用全局递增Flyway版本，并在文件名和脚本头中引用归属业务主版本。

### 5.6 数据留存与清理

平台数据处理遵守[平台架构决策](../decisions/架构决策.md)，并执行以下强制要求：

- 交换记录、配置、对账、告警和审计只保存完成运行、追溯和管理所需的最小字段，不以平台数据库复制HIS、电子病历、LIS、PACS或基层业务库。
- 经批准的基层机构、人员、科室和目录基础数据使用独立业务表保存，记录来源、源标识、版本或更新时间、同步时间和有效状态；不得与交换正文混存。
- 即时查询的完整请求和响应只在请求期间处理，默认不持久化。业务正文不得进入运行日志、审计日志、错误响应、浏览器本地存储、普通缓存、测试样例或问题附件。
- 写入类接口只有在异步发送、服务重启恢复、受控补偿或结果未知核查确有需要时，才可按逐接口书面批准暂存最小正文。未批准时不得创建正文存储，也不得宣称具备无法实现的异步恢复能力。
- 正文存储与`exch_exchange_record`等交换记录逻辑隔离，以受控引用关联；正文必须加密，普通查询、列表和日志不得返回。密钥仅保存安全引用，实际值由医院批准的安全方式管理。
- 每项接口必须分别配置交换记录、审计、对账、告警、临时报文和备份副本的留存期限、起算事件、清理规则和责任人。“待确认”是上线阻断项，不使用代码默认值替代书面结论。
- 清理任务采用有限批次，记录计划时间、实际时间、数量、结果和`requestId`。失败必须重试、告警并进入人工处置，不得通过无限延长期限掩盖失败。
- 清理正文后可保留必要的业务引用、状态、结果码、摘要校验值及清理审计，但不得保留可还原正文的副本。备份恢复后仍执行原到期规则。
- 查看、解密、导出暂存正文和人工再次处理属于敏感操作，必须进行服务端授权并记录主体、机构、目的、对象、结果和时间。

## 六、安全、配置与运行记录

### 6.1 权限与数据保护

- 权限至少区分用户、角色、所属机构、功能、接口、数据范围和操作类型。
- 基层卫生院默认只能访问本机构获准数据；跨机构查询、导出、再次处理和配置发布应单独授权并审计。
- 接口账号按系统和环境分别设置，测试凭证不得用于生产，离职或合作结束后及时停用。
- 密码、Token和证书私钥不得写入代码、普通配置文件、数据库明文字段、前端包或日志。
- 非生产环境原则上使用脱敏数据；确需使用生产数据时，应取得审批并落实访问、期限和清理要求。
- 嵌入页面使用短时、一次性或可撤销的登录凭据，不在URL中传递患者敏感信息和长期凭证。

### 6.2 配置管理

配置分为三类：非敏感默认配置随代码管理；环境配置由部署目录或配置管理工具维护；密码和证书只保存安全引用，实际值由医院指定方式保管。配置变更必须记录变更内容、原因、申请人、复核人、生效时间和恢复值。

生产环境不得使用`latest`、开发分支配置或无法确定内容的安装包。接口地址、超时、再次处理次数等配置必须设定合理范围，防止错误配置影响HIS或基层系统。

### 6.3 日志、审计与告警

运行日志至少包含时间、级别、应用、环境、事件、`requestId`、`traceId`、机构、接口和结果。不得记录密码、Token、Cookie、完整身份证号、完整手机号、患者姓名与证件号组合、未脱敏报文和程序连接密码。

以下操作必须审计：登录失败、敏感查询、导出、人工再次处理、映射变更、接口启停、权限调整、生产配置变更和运维操作。审计记录不得由普通业务用户修改或删除。

至少对服务不可用、接口连续失败、凭证失效、待处理积压、对账差异、数据库空间不足、备份失败和异常访问进行告警。每个告警应明确影响、责任人、处理步骤和恢复条件。

### 6.4 私有化部署

- 开发、测试、联调、生产环境的地址、账号、数据库和日志相互隔离。
- 应用、数据库、管理页面和日志部署在医院指定机房或私有云；外部远程访问需经审批并留痕。
- 平台可与HIS复用符合上述补丁和风险要求的SQL Server 2012 SP4服务器或实例，但必须使用独立平台数据库和读写账号；县医院HIS读取平台库视图使用另一只读账号，并验证查询连接、批量和备份不会影响平台与HIS。
- 部署前明确服务器、端口、域名或地址、证书、时间同步、防火墙、备份目录、监控和值守联系人。
- 数据库、配置和必要文件按医院制度备份；上线前至少完成一次可复核的恢复验证。

## 七、开发、测试与发布规范

### 7.1 工作项进入开发的条件

每个工作项开始前应明确目标、范围外内容、责任人、受影响系统、接口版本、数据样例、权限要求、失败处理和验收方法。涉及外部接口且条件不具备的，不进入功能开发；可以先完成与具体字段无关的平台公共能力。

### 7.2 测试层级

| 测试层级 | 验证内容 | 必要证据 |
|---|---|---|
| 单元测试 | 参数检查、转换规则、防重复键、状态变化和权限判断 | 与代码同时提交的测试结果 |
| 接口合同测试 | 字段、类型、必填、值域、身份验证和结果码 | 正式版本、脱敏样例和双方结果 |
| 数据库集成测试 | SQL Server脚本、事务、并发、索引、正文隔离和数据清理 | 可重复环境、到期清理与清理失败记录 |
| 完整过程测试 | 基层发起、平台处理、县医院办理、结果返回和审计 | 业务单号、页面、接口、数据库和日志相互对应 |
| 异常测试 | 重复、超时、断网、目标系统不可用、服务重启和结果未知 | 再次处理、对账或人工处置记录 |
| 安全与性能测试 | 越权、敏感信息、正文泄露、接口并发、清理批次和资源使用 | 测试条件、数据规模、结果和问题关闭记录 |

模拟数据可以用于代码分支测试，但不得替代正式脱敏样例、真实组件集成或双方联调证据。

### 7.3 自动检查与合并条件

项目应建立统一命令完成格式检查、编译、单元测试、接口合同检查、数据库脚本检查、前后端构建和敏感信息扫描。SQL静态检查必须覆盖一个业务一个主版本、补丁归属与数量、命名、脚本头以及表、字段、约束和索引说明。具体命令以仓库`README.md`为准；只有脚本已提交且实际运行通过后，才能说明自动检查已经建立。

代码合并前必须满足：需求和P0结论明确；实现符合模块边界；测试通过；接口、数据库、配置和文档同步更新；无明文凭证和可识别患者数据；另一名开发人员完成复核。

### 7.4 版本与发布

- 项目交付版本采用`v主版本.次版本.修订版本`。不兼容的接口或数据变更升级主版本，向后兼容的新能力升级次版本，兼容性修复升级修订版本。
- 文档内部修订使用`YYYYMMDD.N`，同一天从`.1`顺序增加。内部修订不替代正式交付版本。
- 接口合同、字段映射、数据库脚本、配置、应用包和前端包分别记录版本或校验值，发布清单建立对应关系。
- 生产发布必须使用经过测试的同一批次制品，记录发布时间、操作人、版本、数据库脚本、配置、验证结果和恢复目标。
- 发布前形成备份和恢复步骤；出现患者错配、越权、敏感信息泄露、重复写入或结果无法确认时，立即停止相关写入并恢复原业务流程。

## 八、两个月执行与交付要求

### 8.1 人员与责任

| 工作组 | 人数 | 工程责任 |
|---|---:|---|
| 县人民医院HIS改造组 | 2人 | 平台库基础数据视图定义、HIS只读访问、其他业务接口、页面入口及联调 |
| 中间接口平台组 | 2人 | 后台、管理端、嵌入页面、接口适配、数据库、部署和技术资料 |
| 项目对接与协调 | 1人 | 范围、P0、计划、跨方协调、问题台账、培训和验收材料 |

HIS组和平台组各明确一名主责和一名备份。基层卫生院、电子病历、LIS、PACS、网络安全和接口提供方分别指定固定联系人。每项任务只设置一个执行责任方和一个验收责任方。

### 8.2 八周工程控制点

| 周期 | 工程控制点 | 必须形成的证据 |
|---|---|---|
| 第1周 | 冻结范围、建立接口台账、登记全部P0、确定工程结构和环境 | 范围基线、P0清单、责任表、仓库和环境记录 |
| 第2周 | 关闭P0，确认合同、样例、网络、凭证、患者和基础信息规则 | 书面结论、脱敏样例、连通记录、字段与编码表 |
| 第2至3周 | 建立单体应用、平台数据库、权限、管理端和部署基线 | 可运行基础版本、数据库脚本、构建与部署记录 |
| 第3至6周 | 按业务领域并行完成接口、HIS改造、页面和联调 | 接口完成清单、代码评审、联调和问题关闭记录 |
| 第6至7周 | 完成完整过程、异常、对账、安全、性能和恢复测试 | 测试报告、对账记录、安全检查和恢复验证 |
| 第7至8周 | 试运行、上线、培训、资料移交和终验 | 试运行记录、发布清单、培训记录和验收报告 |

### 8.3 完成定义

一项接口或功能只有同时满足以下条件才计为完成：

1. 范围、合同、责任人和验收场景已经确认；
2. 代码、配置、字段映射和数据库脚本已纳入版本管理；
3. 正常、重复、失败、超时、结果未知和权限场景已验证；
4. 能够按机构、接口和业务单号查询全过程并完成对账；
5. 日志、审计和告警能够定位问题且不泄露敏感信息；
6. 双方使用正式脱敏样例或获批真实业务场景完成联调；
7. 评审、测试、部署和验收证据已归档；
8. 恢复原流程或通过后续版本修复的措施明确。
9. 数据分类、留存期限、正文暂存依据、清理和清理失败处置已确认并验证。

### 8.4 上线不可放宽项

- 不得存在患者或机构错误对应。
- 不得存在未授权跨机构访问、敏感数据泄露或明文凭证。
- 写入结果不明确时不得直接重复写入。
- 立项范围内接口未完成业务完整过程验证时不得按完成验收。
- 数据库备份、恢复、监控和问题联系人未验证时不得上线。
- 数据留存期限、正文暂存审批或到期清理未确认、未验证时不得上线。
- 接口条件不具备的事项必须由项目负责人取得正式处理结论，不得以备注代替解决。
