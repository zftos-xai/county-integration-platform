# 正式菜单完成标准

本规范是[业务功能完成与验收标准](业务功能完成与验收标准.md)在正式菜单和页面上的专项要求，用于防止“已有菜单、一级页面或接口调用”被误判为业务完成。正式菜单必须以一个可独立验收的业务功能交付，并在 `web-admin/menu-delivery-status.json` 登记真实阶段。页面通过本规范后，仍须满足通用标准中适用的业务操作、停止使用方式和业务负责人确认要求，才能称为“业务已完善”。

## 1. 阶段定义

| 阶段 | 判定条件 | 是否可称完成 |
| --- | --- | --- |
| 仅有计划 | 仅有需求或原型；下一步是完成后端实现 | 否 |
| 后端已实现 | 后端接口规范、权限、数据范围和审计已具备；下一步是接入前端 | 否 |
| 前端已接入 | 页面地址、导航、页面状态、真实 API、表单或详情、错误处理及自动化测试已接入；下一步是验证写入和回读 | 否 |
| 已验证写入和回读 | 已在受控真实环境完成读取、写入、刷新回读、审计查询和清理恢复；下一步是业务验收 | 否 |
| 业务已验收 | 管理员、只读、无权限、跨机构、冲突和后端不可用场景通过，业务负责人已确认 | 是 |

正式导航不得出现“仅有计划”、“后端已实现”或占位页面。只有“业务已验收”可以在计划、进度和交付说明中称为“已完成”。

## 2. 每个菜单必须包含的内容

每个菜单必须同时具备：

1. 页面标题、读取权限和直接输入 URL 时的访问权限检查；
2. 正式导航入口及服务端权限校验；
3. 加载、空数据、筛选无结果、失败、401、403、409和后端不可用状态；
4. 列表或工作台、详情、必要的新增/编辑/启停等业务动作；
5. API 类型、运行时响应格式校验、请求格式定义、表单数据和后端校验；
6. 可访问机构、敏感字段、并发版本、防重复提交及结果未知处理；
7. 成功写入后的刷新回读，以及可按对象和请求编号查询、已删除或遮盖敏感字段的审计记录；
8. API、表单、权限、错误恢复和缺陷回归测试；
9. 桌面浏览器的布局、焦点、键盘、控制台和网络复验；
10. 可逆测试数据的清理或恢复确认。

缺少任一适用环节时，交付阶段不得升级。

## 3. 真实写入、回读和审计证据

阶段为“已验证写入和回读”时，验收记录至少包含：测试前数据、测试用户与权限、操作对象、请求结果、刷新或重新进入后的回读、对应审计事件、清理动作、恢复后的最终状态、浏览器与服务端版本。网络响应成功但没有回读和审计，不能说明整个处理过程已完成。

禁止在证据中保存密码、Token、Cookie、患者正文、完整身份信息、敏感参数值、服务地址凭证或生产秘密。测试对象必须使用明显的合成标识。

## 4. 变更与评审

- 新增菜单时，必须同步登记交付阶段并通过 `node tools/verify-menu-delivery.mjs`。
- 菜单新增业务动作时，必须同步页面、API、后端授权、审计动作、测试和回读证据。
- 阶段升级必须在同一变更中附带证据；不得先改状态、后补验证。
- “业务已验收”必须记录验收决定并由业务负责人复核；静态脚本只校验材料完整性，不代替人工验收。
- 登录认证、用户权限、机构范围、敏感配置和审计相关菜单仍须另一名开发人员复核。
