# 1. 项目定位与执行摘要

建议以“院内集成平台”为唯一对外接口边界，现有 C/S HIS 工作站只负责业务入口和结果展示，不直接持有云平台密钥、不直接访问外网，也不在客户端实现重试。集成平台统一完成 REST/JSON 与 SOAP WebService 两套协议适配、身份验证、数据映射、异步队列、审计、对账和异常失败后补救。

本项目仍处于启动前准备阶段。本文描述目标、范围和开始条件，不代表接口已经获批、系统已经建成或真实环境已经验收。项目启动后，以已确认的接口规范、环境验证、联调记录和书面验收结论更新执行状态。

原 Excel 不是可直接据此开发的最终范围：其中健康云21行、基层HIS 53行，共74行；通知正文称21+52=73个。基层HIS中的远程会诊复用了300-001/300-002，而规范另有一个无独立交易码的“报告跨机构调阅”功能。项目必须分别按“接口行、唯一交易码、业务功能”确认各项数量。

首轮范围需做三项修正：云平台登录、区划和用户接口，以及基层100-*基础接口，必须在开工前准备完成；电子病历400-003虽在Excel标记“不做”，但规范明确要求病历回写，应在病历实施阶段补齐；报告跨机构调阅需补入范围确认。

## 1.1 核心结论

- 健康云21个接口全部由院内集成平台主动调用省云平台，采用HTTPS、REST/JSON、hie_secret签名、c_token与登录token。

- 基层系统在其应用服务器上提供`PHIS_Interface` WebService，院内集成平台作为接入方按`TradeCode`调用；电子病历、单点登录、远程会诊、报告互认还包含基层HIS打开第三方页面或向第三方回写的反向流程。

- 基层机构基础数据保存到平台独立数据库；县医院HIS厂商在平台库上建立受控视图，县医院HIS使用只读账号读取，不为同一目的调用平台业务接口。

- 原规范没有形成完整的重复提交不产生重复结果、超时、重试、连续失败后自动暂停请求、失败后补救和监控约定，必须由院内集成平台补齐。

- 规范内存在多处必须解决的冲突，尤其是500-003/500-004、700-003/700-004、300-003成功值，以及PHIS_Interface/HIS_Interface；未书面确认前不得进入生产。

- 生产环境应使用专网或严格IP白名单、TLS、等保要求、最小权限和敏感日志脱敏；测试文档中的HTTP地址、账号、验证码只用于隔离联调。

# 3. 目标架构

## 3.1 逻辑架构

基层机构基础数据按正式来源数据说明同步到平台独立数据库，再通过平台库受控视图提供给县医院HIS只读访问。其他业务由院内集成平台按已确认的接口规范调用省健康档案云平台和基层系统接口。电子病历、单点登录、远程会诊和报告等存在反向页面或回写的场景，经医院边界接入区/API网关进入平台或约定页面；禁止基层系统直连县医院HIS数据库，也禁止县医院HIS通过视图写入平台基础表。

### 两条主要数据传递过程

```text
基础数据处理：基层系统 -> 中间接口平台 -> 平台数据库基础数据表 -> 平台库受控只读视图 -> 县医院HIS
业务接口处理：县医院HIS及相关系统 ⇄ 中间接口平台 ⇄ 基层系统PHIS_Interface及约定页面
```

基础数据进入平台的传输方式以正式来源数据说明为准，平台到县医院HIS的读取方式固定为数据库视图。其他业务统一进入接口规范、交换记录、状态追踪和对账范围。

| 组件 | 职责 |
| --- | --- |
| API网关/边界代理 | TLS终止、IP白名单、限流、报文大小限制、访问审计；SOAP入口仅开放所需方法 |
| 健康云接入程序 | REST服务地址、MD5签名、token缓存与刷新、0/200成功码兼容、字段字典转换 |
| 基层系统接入程序 | 作为客户端调用基层系统`PHIS_Interface`统一入口，完成按TradeCode分发请求、SOAP/XML与JSON字符串解析和响应格式统一 |
| 平台库基础数据视图 | 按县医院HIS厂商确认的字段和范围提供基层基础数据，由县医院HIS只读访问 |
| 基础数据与映射层 | 保存获批的基层机构、人员、科室、目录等来源数据，以及居民身份关联记录、诊断、三大目录和公共卫生字典映射 |
| 可靠消息/出站箱 | 上传、修改、报告回写等写操作异步化；去重、重试、死信和人工重放 |
| 目标系统返回结果与对账库 | 保存云平台id/sjlyId、外部流水、原始报文摘要、状态轨迹和日对账结果 |
| 运维控制台 | 接口开关、版本化配置、凭证轮换、失败检索、脱敏重放、指标与告警 |

## 3.3 C/S工作站改造原则

- 工作站只调用院内服务，使用当前登录用户和就诊信息，不保存省平台账号、token或验证码。

- 档案摘要、电子病历、互认报告采用按需入口；长耗时操作异步提交并显示可追踪状态。

- 上传/修改在业务审核完成后触发；未通过字段校验的数据进入待处理列表，不阻塞HIS主流程。

- PACS/LIS/心电报告回写必须在报告审核后执行，撤销或修订通过版本号控制。

## 3.4 技术选型和版本与部署隔离

- 后端统一使用Java 17、Spring Boot 3.5和MyBatis，采用模块化单体。
- 数据库统一使用Microsoft SQL Server 2012 SP4、兼容级别110，并安装医院批准的最新可用安全/GDR更新。
- 页面使用Vue 3和TypeScript，分为管理端与工作站嵌入端。
- 平台库可以与县医院HIS数据库位于同一服务器或同一SQL Server实例，但必须使用独立数据库、账号、备份和维护计划。
- SQL Server 2012使用医院提供的Windows Server或现有实例，不部署SQL Server Linux容器。

# 4. 接口调用与数据流

## 4.1 健康档案云平台

调用链为：取得接入授权 -> 登录获取access token -> 缓存区划与本机构用户 -> HIS业务数据校验与字典转换 -> POST上传 -> 事务保存id/sjlyId/jtId目标系统返回结果 -> 后续PUT修改。所有调用携带hie_event_code、hie_app_key、hie_time_stamp、hie_secret，以及c_token和accesstoken请求头。

hie_secret按文档要求计算md5(hie_app_key+授权key+hie_event_code+hie_time_stamp)。平台允许时间偏差窗口最长半小时，但医院服务器仍应统一NTP校时；生产不得因兼容MD5而放宽网络边界控制。

## 4.2 基层HIS WebService

除县医院HIS读取基层基础数据外，基层系统在`http(s)://{基层系统应用服务器}:端口/WebService.asmx`提供业务接口，院内集成平台作为客户端经SOAP POST调用统一入口。一级参数为TradeCode与InputParameter，后者是JSON字符串。适配层必须同时容忍Result/result、Msg/msg、数值/字符串和Msg嵌套JSON字符串等历史差异，并将其统一转换为内部统一响应。审计默认只留必要摘要和业务引用；原始报文只有在单接口已批准最小字段、加密、访问、期限和自动清理规则时才可限时暂存，具体执行 [平台数据留存边界](../decisions/架构决策.md)。

基层机构、人员、科室、目录等基础数据进入平台独立数据库，记录来源、源标识、版本或更新时间、同步时间和有效状态。其进入平台的具体来源方式、字段、全量初始化、增量更新和停用含义以已确认的接口规范为准，不因参考文档存在100-*交易码而预先认定来源方式。

## 4.3 平台库基层基础数据视图

基层机构基础数据保存到平台独立数据库。县医院HIS厂商根据已确认的接口规范在平台库建立或维护受控视图，县医院HIS使用与平台应用账号分离的只读账号查询。每个视图必须确认消费方、最小字段、过滤范围、查询频率、单次上限、允许时段、版本兼容和已确认的性能参考值。视图只承担县医院HIS读取基层基础数据，其他业务通过正式接口交互。

## 4.4 关键完整业务处理过程

| 业务 | 必须验证的步骤 |
| --- | --- |
| 健康档案 | 经正式接口或其他获批来源取得数据 -> 校验/映射 -> 上传健康云 -> 目标系统返回结果落库 -> 修改引用id/sjlyId -> 对账 |
| 基层基础数据 | 经正式来源取得 -> 校验来源版本 -> 平台独立库新增或更新 -> 平台库受控视图 -> 县医院HIS只读查询 -> 定期校准 |
| PACS/LIS/心电 | 医技站按申请单号拉取 -> 执行 -> 审核报告 -> FHIR+Base64回写 -> HIS展示/状态更新 |
| 电子病历 | HIS携业务ID和短效token打开EMR -> EMR验token -> 查询患者/诊断/护理 -> 保存签名 -> 400-003回写 |
| 双向转诊 | 上转查询300-001/002；下转先取机构信息，再以FHIR Base64调用300-003并保存目标系统返回结果 |
| 便民挂缴查 | 基础目录与虚拟收费员 -> 挂号/缴费 -> 未知结果查状态 -> 原路退费协调 -> 200-015日对账 |
| 报告互认 | HIS按患者身份查询有无报告 -> 展示状态 -> 打开互认平台报告页；需明确授权和最小披露 |

## 4.5 统一处理状态与审计链

院内集成平台对所有写操作使用统一状态：RECEIVED（已接收）-> VALIDATED（已校验）-> SENT（已发送）-> ACKNOWLEDGED（已取得明确目标系统返回结果）-> RECONCILED（已对账）。可恢复失败进入RETRY_WAIT，不可自动判断的超时或冲突进入MANUAL_REVIEW，明确业务拒绝进入REJECTED。只有取得可核验目标系统返回结果才能标记ACKNOWLEDGED，HTTP 200本身不等于业务成功。

每次状态迁移至少记录requestId、机构、接口代码、源业务主键、报文摘要、目标地址标识、开始/结束时间、响应代码、重试次数、操作者或服务身份和配置版本。敏感原文按最小化原则加密保存，并设置访问审批和保留期限。

# 5. 可靠性与安全设计

## 5.1 防止重复提交与失败后补救

- 上传：以机构+源系统+源主键+业务类型建立唯一键；平台目标系统返回结果与本地状态同事务保存。

- 修改：以平台id+sjlyId+源版本号去重；发生版本冲突时停止自动覆盖并转人工。

- 报告/病历回写：以申请单或业务ID+文档类型+版本建立唯一键，重复请求返回既有处理结果。

- 挂号/缴费/退费：使用厂商唯一标识和外部业务单号；超时结果未知时先查挂号、已缴费或账单状态，禁止直接重发。

- 查询：仅对网络异常、超时和5xx执行最多2次指数退避重试；身份验证、参数和权限错误不重试。

## 5.2 超时与容量

建议连接超时3秒、普通查询读取15秒、写操作30秒、大病历/护理报文60秒。健康云缺省QPS=300，但医院网关应按业务和厂商设置更低的配额并支持动态调整。轮询类接口需加入抖动，避免多个终端同时整秒请求。

## 5.3 安全控制

- 密钥、c_token、平台账号和基层验证码放入集中凭证库，按环境和机构隔离，禁止写入客户端、源码和普通日志。

- 日志默认脱敏姓名、证件号、电话、地址、病历和报告；排障查看明文需审批并全程审计。

- 单点登录token应一次性、短时有效并绑定用户、机构、业务ID与目标系统；URL中只放不可逆短票据。

- 外部调用经专网或IP白名单和TLS，SOAP解析关闭外部实体，限制XML/JSON/Base64及解压后大小。

- 按接口事件码/交易码授予最小权限；离职人员、停用机构和过期授权应自动失效。

| 高 | 400-003在Excel不做，但规范要求病历回写 | 纳入电子病历验收范围 |
| 高 | 接口总数是73还是74尚未统一、交易码被复用、有功能没有交易码 | 申请表按业务功能列明，验收表同时记录行数和唯一交易码数 |
| 高 | 日期、大小写、Msg类型、路径存在多种格式 | 适配层配置化容错，医院内部模型保持严格类型 |

## 7.2 责任与里程碑控制

每项接口仅设一个执行责任方和一个验收责任方。医院信息科维护范围、未解决事项和确认版本；厂商按对照表登记负责人、计划日期、当前状态和验收材料链接。状态只能在“未开始、接口资料不完整、联调环境未准备、开发中、联调中、待验收、已通过、暂缓”之间变更，口头说明完成不能代替书面验收记录。

| 里程碑 | 主责 | 完成证据 |
| --- | --- | --- |
| M0 范围冻结 | 医院信息科 | 批准的申请表、接口范围和不做项决策记录 |
| M1 接口资料确认 | 省/基层平台方+集成平台厂商 | WSDL/OpenAPI、勘误单、样例、版本指纹 |
| M2 环境就绪 | 医院信息科+网络安全 | 连通性、TLS、白名单、NTP和凭证验证记录 |
| M3 单接口通过 | 对应开发厂商 | 请求响应、断言、日志traceId和缺陷关闭记录 |
| M4 业务验收 | 业务科室+信息科 | 从来源系统请求到目标系统结果的场景、数据一致性、失败后补救和对账报告 |
| M5 允许生产上线 | 医院变更审批责任人 | 上线检查表、回退演练、监控值班和签字记录 |

## 7.3 项目团队与八周计划

核心团队按5人配置：县医院HIS改造2人、中间接口平台2人、项目对接协调1人。医院信息科、业务科室、安全运维、基层卫生院、基层系统提供方及相关业务系统厂商另行指定固定联系人。每项任务只设置一个执行责任方和一个验收责任方。

| 周期 | 主要工作 | 退出条件 |
| --- | --- | --- |
| 第1周 | 冻结范围、责任人、未解决事项和升级路径 | 形成书面已确认的范围与责任表 |
| 第2周 | 确认接口规范、样例、网络、账号、基础数据及视图要求 | 开工前的条件具备，未具备的事项明确暂停原因 |
| 第2至3周 | 建立平台、数据库、权限和测试环境 | 基础版本可部署并通过工程检查 |
| 第3至6周 | 按业务域并行开发和联调 | 单接口证据、缺陷和状态可追踪 |
| 第6至7周 | 验证请求、处理结果、错误恢复、对账、安全和性能 | 各项业务达到验收条件 |
| 第7至8周 | 试运行、回退演练、培训、上线和移交 | 取得医院书面验收结论 |

八周计划以第1周范围冻结、正式资料和环境第2周具备、核心人员稳定到位及厂商并行配合为前提。条件延迟时调整范围或计划必须走正式变更，不得降低数据安全和验收标准。

# 8. 测试与验收

- 接口兼容性测试：每个事件码/交易码覆盖必填、边界、空结果、非法字典、大小写与响应类型变体。

- 业务测试：按患者、就诊、申请单、报告、病历、转诊和收费，分别发起真实请求并核对目标系统的处理结果。

- 可靠性测试：重复请求、服务超时、断网、进程重启、目标系统返回结果丢失、消息积压、死信重放和对账差异。

- 安全测试：越权、过期token、签名错误、重放、恶意XML、超大Base64、日志脱敏和凭证轮换。

- 性能测试：按峰值并发与轮询终端数压测，验证网关限流、连接池、队列积压和HIS数据库负载。

- 上线条件：未解决事项已解决，开工准备阶段的功能稳定运行，已演练回退方案，已接入监控告警，业务部门与信息科共同签字。

## 8.1 建议指标

| 指标 | 目标 |
| --- | --- |
| 查询接口成功率 | 不低于99.9%（剔除明确业务拒绝） |
| 写入最终成功率 | 经自动失败后补救后不低于99.95% |
| 重复业务写入 | 0 |
| 患者/机构/人员错配 | 0 |
| P95响应时间 | 普通查询不高于3秒；大病历按联调时确认的参考值 |
| 故障可追踪性 | 100%请求具备requestId/traceId和状态轨迹 |

## 8.2 验收证据最小集合

每个接口至少保留：接口版本或文件哈希、脱敏请求与响应、预期断言、实际结果、requestId/traceId、执行时间、环境、配置版本、执行人、缺陷编号和复测结论。写接口还应提供重复请求、超时未知、重放、目标系统返回结果落库和对账证据；页面跳转类还应提供短票据失效、越权和返回路径测试。

# 9. 上线与回退

上线采用机构/业务域分机构、分业务类别逐步上线。接口、事件码、交易码、服务地址、成功码和超时均配置化；每个写入业务均有独立开关。回退时先停新写入，再清空或冻结队列，保留查询功能和完整台账，不删除已生成的目标系统返回结果映射。

上线后前两周每日核对上传、报告回写、病历回写和异常队列；随后转为自动日报与周度抽查。任何规范变更都先更新PRD、技术设计和接口兼容性测试，再按变更流程发布。

## 9.1 上线检查与量化回退触发

| 类别 | 上线前检查 | 触发回退/停写条件 |
| --- | --- | --- |
| 数据正确性 | 患者、机构、人员、申请单和报告抽样100%匹配 | 发现患者错配、跨机构越权或不可逆错误写入，立即停写 |
| 业务成功率 | 核心写入在试运行窗口达到约定最终成功率 | 连续15分钟最终成功率低于99%，且失败后补救无法恢复 |
| 性能容量 | 峰值压测通过，HIS数据库和队列有容量余量 | P95连续15分钟超过已确认参考值的2倍，或队列预计2小时无法清空 |
| 安全 | 权限、脱敏、证书、凭证轮换和审计验证通过 | 出现凭证泄露、未授权访问或敏感日志外泄 |
| 可运维性 | 告警、值班、重放、对账和回退演练完成 | 关键告警失效、状态不可追踪或无法执行已批准回退步骤 |

实际阈值应在容量测试和业务评审后写入上线检查表；上表未确认的数值仅作为评审起点。回退动作、审批人、执行人和恢复条件必须在变更单中具体到业务域与机构。
