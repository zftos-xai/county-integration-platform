## 1. 文档规则

### 1.1 事实优先级

需求发生冲突时，按以下顺序处理：

1. 项目负责人或用户已经明确确认的项目事实；
2. 原《接口列表.xlsx》中的“可做/不做、优先顺序、实现方式、功能改造”；
3. 上游V1.0规范明确写出的接口用途、调用方向和接入步骤；
4. 已确认的总体架构与数据库边界；
5. 原型只用于界面走查，不能单独证明业务需求已经成立。

以下内容不能直接写成开发需求：

- 通用集成平台通常具备、但本项目没有确认的功能；
- 根据接口名称猜测出的业务触发时点和流程；
- 原型合成数据表现出的虚构运行结果；
- 二次整理材料中没有原始资料支撑的异步、重试、对账和验收结论；
- 尚未确定的内部API路径、数据库表和字段。

### 1.2 已确认不建设的功能

整体项目不建设：

- 接入申请或审批流程；
- 机构权限配置页面；
- 接口登记、接口注册中心或接口台账页面；
- 合同文件上传、签署或版本管理；
- 为展示技术过程而设计的“已受理、已校验、已发送、等待重试、已对账”等交换状态。

### 1.3 本PRD与技术设计的边界

本PRD定义实际业务场景、系统职责、输入输出和验收结果。内部API路径、Java类、数据库表、队列、调度任务和重试算法属于技术设计，只有在业务需求确认后才能确定。

### 1.4 最新接口清单分析结论

本次提供的最新《接口列表.xlsx》与仓库原清单相比：

- 接口范围、事件码/交易码、“可做/不做”和优先顺序均未变更；
- `Sheet2`中的健康档案字段清单没有变更；
- `Sheet1`新增“对于HIS对象”列，补充了健康档案、健康体检、基础数据、双向转诊、PACS、LIS和心电相关对象名；
- 新增了“是否保存每次调用的XML/JSON”和“健康体检数组是否拆分独立视图”两个问题，两者均是待决策项，不能按已确认需求实现；
- 清单补充说明“HIS系统调用中间接口后需要把返回数据写入HIS相应表”，但未指明每个接口的写入责任方、表名和字段映射，因此必须逐接口确认。

本次仅根据上述增量调整数据对象、开发输入、阻断条件和待确认事项，不扩大业务范围。

## 2. 项目目标和系统边界

项目建设两类能力：

1. 基层机构基础数据进入平台数据库，县医院HIS通过平台库受控只读视图读取；
2. 县医院HIS及相关系统通过中间接口平台调用健康档案云平台和基层HIS正式接口。

```text
基础数据：基层数据来源 → 中间接口平台 → 平台数据库 → 只读视图 → 县医院HIS

业务接口：县医院HIS及相关系统 ⇄ 中间接口平台 ⇄ 健康档案云平台/基层HIS
```

边界要求：

- 县医院HIS不直接写平台基础数据表；
- 基础数据读取之外的业务不通过数据库视图绕过正式接口；
- 中间接口平台不替代HIS、电子病历、PACS、LIS、心电等业务系统；
- 浏览器和工作站不保存外部平台长期凭证；
- 业务正文默认不作为普通运行记录保存。

## 4. 开发启动

开发启动是把人员、仓库、数据库、测试环境和首个真实业务场景准备到可编码状态，不是项目交付阶段，也不改变第3章的整体范围和业务优先级。

### 4.1 启动目标

开发启动完成时应达到：

1. 后端、管理端和嵌入端能够在开发人员环境中构建；
2. 后端能够连接SQL Server 2012 SP4开发或测试实例并执行基线迁移；
3. 从优先顺序1中确定一个真实业务场景作为首个纵向开发切片；
4. 该场景具备实际调用方、目标系统、测试地址、脱敏样例和成功/失败返回样例；
5. 前端或调用方能够发起该场景，平台能够调用真实测试接口并保存运行记录；
6. 团队能够使用requestId定位真实成功、失败和无响应调用；外部环境无法提供的测试条件必须如实登记。

### 4.2 启动人员与职责

| 角色 | 启动阶段职责 | 必须输出 |
| --- | --- | --- |
| 项目对接负责人 | 确认首个开发场景、协调HIS和外部系统测试条件 | 首个场景结论、联系人和问题清单 |
| 中间接口平台开发 | 建立本地环境、数据库连接、外部调用和运行记录 | 可运行工程、配置说明和真实调用记录 |
| HIS开发 | 提供实际页面入口、视图或调用方式，处理接口返回 | 页面/视图说明、调用样例和返回处理位置 |
| 外部系统接口人员 | 提供测试地址、凭证交付方式和返回样例 | 可访问测试接口及正常、失败样例 |
| 测试人员 | 把真实样例转为测试用例并复核结果 | 成功、失败、无响应测试记录 |

### 4.3 启动工作包

#### ST-01 仓库与构建基线

执行内容：

- 安装JDK 17、Maven 3.9、Node.js 22和npm 11；
- 执行`npm install`；
- 执行管理端、嵌入端类型检查和生产构建；
- 执行后端Maven验证；
- 记录工具版本、命令、结果和未通过原因。

当前已知问题：管理端`FoundationDataPanel.vue`引用了未定义的`selectedView`，生产构建未通过。该问题必须在业务功能开发前修复。后端验证需要在安装Maven的标准开发环境重新执行，当前不得宣称已经通过。

完成条件：统一验证命令能够执行，前后端构建通过，失败时能定位到具体文件或测试。

#### ST-02 SQL Server开发基线

执行内容：

- 由医院或项目环境提供SQL Server 2012 SP4实例，兼容级别110；
- 建立独立平台数据库和开发账号；
- 通过环境变量配置连接，不在仓库保存密码；
- 执行现有基线迁移；
- 验证应用账号不能修改HIS业务表；
- 在HIS测试库核对第5.9节对象是否存在，并记录对象类型、Schema、主键/关联键、读写方向和授权方式；
- 记录数据库版本、兼容级别、迁移结果和连接方式。

完成条件：后端可以启动、迁移成功、基础查询可执行，并有可复核的SQL Server版本证据。

#### ST-03 开发与测试配置

执行内容：

- 区分本地开发配置、医院测试环境配置和生产配置；
- 外部URL、账号、验证码、token和数据库密码只通过环境配置或医院批准的安全方式提供；
- 仓库只保留非敏感示例配置；
- 为每个已接入的目标系统配置明确的连接超时和读取超时，数值以实际联调结论为准。

完成条件：开发人员无需修改代码即可切换本地与测试配置，代码、日志和前端包中不存在明文凭证。

#### ST-04 首个业务场景选择

首个纵向切片必须从原清单“优先顺序1”中选择，不由开发人员自行扩展范围。

| 可选场景 | 开始条件 | 最小贯通路径 |
| --- | --- | --- |
| 健康档案或健康体检上传 | 第5.9节所列HIS对象的类型、字段、关联键与读取条件已确认，健康云测试地址和请求返回样例已具备 | 读取一笔脱敏HIS对象数据 → 调用对应POST接口 → 返回实际结果 |
| PACS申请单获取 | 500-002测试地址、验证码和脱敏申请单号已具备 | 输入申请单号 → 调用500-002 → 展示实际申请单或失败结果 |
| LIS申请单获取 | 600-002测试地址、验证码和脱敏申请单号已具备 | 输入申请单号 → 调用600-002 → 展示实际申请单或失败结果 |

选择原则：哪个场景最先具备完整真实输入，就先开发哪个；不能为了赶进度使用虚构字段或模拟成功替代实际联调。

完成条件：项目对接负责人明确一个首个场景、实际使用人、接口人员、测试数据和验收人。

#### ST-05 首个纵向切片开发

中间接口平台开发任务：

1. 实现所选场景的内部调用入口；
2. 按实际样例完成外部报文转换；
3. 调用真实测试接口；
4. 将目标返回判断为成功、失败或无响应；
5. 保存第6章规定的最小运行记录；
6. 返回真实结果和requestId，不返回模拟结果。

HIS或前端开发任务：

1. 在确认的实际入口发起调用；
2. 传递该场景真实需要的业务标识；
3. 显示目标系统实际结果；
4. 失败时显示可供实施人员定位的requestId；
5. 不在浏览器或工作站保存外部系统长期凭证。

测试任务：

1. 使用一组脱敏正常数据验证成功结果；
2. 使用上游确认的错误输入验证失败结果；
3. 使用联调方认可的连接中断或超时测试验证无响应；
4. 核对页面结果、平台运行记录和目标返回一致；
5. 核对日志中没有密码、token、验证码和完整医疗正文。

完成条件：成功、失败、无响应三类结果至少各有一条可复核记录；若外部系统无法提供某类测试条件，应明确记录未验证项，不伪造测试结果。

### 4.4 启动阶段不得开展的工作

- 不同时铺开全部接口；
- 不开发原清单标记“不做”的接口；
- 不先建设审批、机构权限、接口登记和合同版本管理；
- 不根据通用平台经验增加交换状态、自动重试、对账或告警流程；
- 不在真实页面入口、字段和样例未确认时编写对应业务逻辑；
- 不以原型合成数据或Mock成功作为首个纵向切片完成证据。

## 5. 已有事实支撑的业务场景

### 5.1 健康档案和健康体检上传、修改

#### 场景依据

- 原清单明确四个接口为“可做、优先顺序1”；
- 原清单明确实现方式为“HIS提供视图 + 中间接口上传”；
- 健康云规范7.2.3、7.2.4、7.3.1和7.3.2明确上传使用POST、修改使用PUT；
- 原清单备注说明，HIS调用中间接口后需要处理返回数据并写入HIS相应表。

#### 已确认流程

```text
HIS按约定提供健康档案或健康体检视图数据
    ↓
中间接口平台读取约定数据
    ↓
中间接口平台调用健康云上传或修改接口
    ↓
中间接口平台把健康云实际返回结果交给HIS调用方处理
```

#### 开发要求

- 上传和修改必须分别调用原清单指定的事件码和HTTP方法；
- 上传健康档案已给出HIS对象`V_四川_健康档案云_723_上传健康档案`；对象类型、Schema、字段、主键和读取条件仍需在HIS测试库确认；
- 上传健康体检已给出`V_四川_健康档案云_731_上传健康体检`和`V_四川_健康档案云_731_上传健康体检_FMYDATA`两个HIS对象；
- 健康体检存在多个数组字段，开发前必须确认两个对象分别承载哪些字段、关联键、一对多基数、数组顺序和空数组表示；清单中的问句不等于已确定拆分方案；
- 修改健康档案和修改健康体检未给出对应HIS对象，不得默认与上传共用；
- 平台只从已核对的HIS对象读取已确认字段，不得根据对象名或`Sheet2`自行补齐数据映射；
- 平台按健康云规范生成鉴权和业务请求；
- 平台原样保留必要返回码及返回标识，供HIS按约定写入相应表；
- 页面只展示真实调用结果，不虚构业务审核、异步队列、自动补发或对账流程；
- 具体触发按钮、触发时点、读取条件、修改接口数据对象和HIS回写表在开发前由HIS厂商确认。

#### 验收依据

- 使用双方确认的HIS对象脱敏样例生成请求；
- 上传调用使用POST，修改调用使用PUT；
- 请求字段和返回结果与健康云规范及联调样例一致；
- HIS能够取得并处理健康云实际返回值；
- 调用失败时页面或调用方获得真实错误信息和requestId。

### 5.2 PACS检查业务

#### 场景依据

上游规范6.5.0明确写出：患者到医技站后，工作人员输入申请单号，后端调用500-002获取申请单数据；完成后调用500-003向HIS回写报告。

#### 已确认流程

```text

    ↓

    ↓

    ↓

    ↓

    ↓
```

500-001用于查询指定机构下的检查项目包和明细。

#### 开发要求

- 500-002按上游规范接收机构ID、申请单ID、业务ID、门诊号、住院号和验证码；

- 输入有效申请单号可以取得规范所列申请单数据；
- 无效申请单号、验证码错误和目标接口不可用分别显示真实结果；
- 使用确认后的实际交易码成功回写一份脱敏检查报告；
- HIS返回失败时，平台显示原始业务错误含义，不显示成功。

## 6. 运行记录与交换结果

### 6.1 实际运维需求

平台需要让实施和运维人员回答：某个接口是否调用、何时调用、调用哪个目标、传入哪个业务标识、目标返回成功还是失败、失败原因是什么。

每次实际接口调用至少记录：

- requestId；
- 接口事件码或交易码；
- 调用时间；
- 调用方和目标系统标识；
- 不包含患者正文的业务记录引用；
- 目标返回码和必要结果说明；
- 调用耗时；
- 通信异常摘要。

### 6.2 交换结果

只允许以下三个结果，不设计技术过程状态：

| 结果 | 适用场景 |
| --- | --- |
| 成功 | 目标系统返回规范或联调确认的业务成功结果 |
| 失败 | 目标系统返回明确业务失败，或请求在发出前发生明确错误 |
| 无响应 | 平台没有取得目标系统业务响应，例如连接超时或连接中断 |

“已受理、已校验、已发送、等待重试、已对账”不属于项目业务场景，不进入数据库结果枚举和页面筛选项。

### 6.3 页面需求

运行记录页面提供：

- 按时间、接口代码、业务记录引用、requestId和结果查询；
- 列表显示调用时间、接口、目标系统、业务记录引用、结果和耗时；
- 详情显示请求摘要、目标返回码、结果说明和通信错误摘要；
- 不显示完整病历、完整报告、密码、token或验证码；
- 对“无响应”只展示事实，不自动显示“目标未处理”或提供通用重发按钮。

具体接口是否允许再次调用以及如何处理无响应，必须在对应业务场景中单独确认，不能建立全平台统一重试流程。

### 6.4 XML/JSON原始报文保存边界

最新清单对“是否在HIS库保存每次中间接口调用的非结构化XML/JSON日志”提出了问题，但没有给出结论。因此：

- 当前不将“在HIS库保存完整XML/JSON”列为已确认需求；
- 默认只保存第6.1节的最小运行记录和脱敏摘要，不保存完整医疗正文；
- 某个接口如果确有排障或审计需要，必须单独确认保存位置、报文范围、脱敏规则、加密、访问权限、保留期和清理方式；
- 未完成上述确认前，不得将完整报文写入HIS业务库或普通应用日志。

## 8. 开发输入与阻断规则

### 8.1 单接口开始编码前需要的事实

| 输入 | 作用 |
| --- | --- |
| 本次实际开发的接口代码 | 防止把“可做”误解为本轮全部开发 |
| 实际调用方和目标系统 | 确认调用方向和部署位置 |
| 测试URL、WSDL或OpenAPI | 建立真实客户端 |
| 脱敏正常和失败样例 | 编写解析和结果判断测试 |
| 实际成功值和失败值 | 只据此判断成功或失败 |
| 页面或业务触发位置 | 确认谁在什么操作下调用接口 |
| HIS对象及数据映射 | 确认对象名、类型、Schema、字段、主键/关联键、读写方向和授权 |
| 返回结果处理位置 | 确认结果展示或写回到哪里 |
| HIS返回数据落表映射 | 确认写入责任方、目标表、唯一键、字段映射和写入失败处理 |

缺少某项时，应明确记录“该接口的这一项尚未确认”，不得用通用平台经验补齐。

### 8.2 已知文档冲突和待澄清点

- PACS回写标题为500-003，参数表写500-004；
- 心电回写标题为700-003，参数表写700-004；
- 300-003成功值说明存在不一致；
- WebService入口同时出现PHIS_Interface和HIS_Interface；
- 原清单不做400-003，但上游电子病历接入指引提示病历需要回写；
- 最新清单给出了HIS对象名，但未给出对象类型、Schema、字段、键、读写方向和授权；
- 修改健康档案、修改健康体检没有对应HIS对象名；
- 健康体检的两个对象与多个数组字段之间的映射未确认；
- “返回数据写入HIS相应表”没有逐接口的责任方、表名和字段映射；
- 是否保存完整XML/JSON调用报文尚未决策。

这些冲突只能通过实际环境、厂商确认或联调样例解决。PRD不得预先选择其中一个值。

### 8.3 单接口开发任务包

每个接口进入编码前建立一个开发任务包。任务包不是接口登记功能，只是开发工作项的必要说明，内容必须来自实际业务和联调资料。

| 项目 | 填写要求 |
| --- | --- |
| 任务编号和接口代码 | 使用项目任务编号及原清单事件码/交易码 |
| 业务场景 | 写明谁在什么实际页面或业务操作中使用，不写抽象“数据交换” |
| 调用方和目标系统 | 写到具体系统，不使用“第三方”等模糊名称 |
| 触发入口 | 页面按钮、后台业务动作或外部系统调用；没有确认则不能编码 |
| 输入来源 | 页面字段、HIS视图、业务表查询结果或上游请求 |
| HIS对象 | 填写实际对象名、类型、Schema、字段、键、读写方向、授权及已完成的环境核对记录 |
| 请求字段 | 引用正式接口资料和脱敏样例，不从原型推导 |
| 成功判断 | 写明测试环境实际成功值和必要返回字段 |
| 失败判断 | 写明实际失败值、错误信息位置和页面展示方式 |
| 无响应处理 | 仅描述本接口已确认的处理方式；未确认时禁止再次调用 |
| 返回结果去向 | 页面展示、返回调用方或由HIS写入的实际位置 |
| HIS返回数据落表 | 填写写入责任方、目标表、唯一键、字段映射和写入失败处理；未确认不得直写HIS |
| 数据保存 | 明确运行记录保存内容；需要正文时必须单独确认 |
| XML/JSON报文 | 默认不保存完整报文；如确需保存，填写脱敏、加密、权限、保留期和清理方式 |
| 前端改造 | 实际页面、按钮、输入、展示和禁用条件 |
| 后端改造 | 内部入口、外部适配、结果转换和运行记录；具体设计另行评审 |
| 测试数据 | 脱敏正常样例、失败样例及可执行的异常测试条件 |
| 验收用例 | 正常、失败、无响应中实际可执行的场景和预期结果 |
| 未确认项 | 责任人和待提供内容，不允许用默认值替代 |

任务包完成并由对应HIS开发、平台开发和测试人员共同核对后，才拆分前端、后端、数据库和测试子任务。

## 9. 开发顺序

开发顺序遵循原清单优先级和业务依赖，不等同于分期交付：

1. 按第4章完成开发启动，选择最先具备真实条件的优先顺序1场景；
2. 完成该场景的开发任务包、技术设计、编码和真实测试，形成可复用的外部调用及运行记录基线；
3. 其余优先顺序1业务按测试条件和页面准备情况依次开发，不在同一时间无条件全部铺开；
4. 确认电子病历页面入口和100-009实际规则后，开发优先顺序2接口；
5. 补充真实页面场景后，开发健康档案摘要和双向转诊；
6. 优先顺序99或“根据实际情况”的接口按已经确认的业务依赖插入开发计划；
7. 原清单“不做”的接口不得因上游规范存在而自动开发。

## 10. 验收原则

一项接口只有满足以下条件才算完成：

1. 对应原清单中的接口代码、优先级和实现方式已经核对；
2. 实际业务触发页面和使用人已经确认；
3. 使用真实测试环境和脱敏样例完成调用；
4. 请求字段、调用方向和目标地址与实际环境一致；
5. 成功和失败均使用目标系统实际返回值判断；
6. 页面展示的结果与实际返回一致；
7. 运行记录可通过requestId和业务记录引用复核；
8. 日志和页面不泄露密码、token、验证码和完整医疗正文；
9. SQL Server相关脚本在SQL Server 2012 SP4、兼容级别110验证；
10. 涉及HIS对象的接口已在目标环境核对对象类型、Schema、字段、键、读写方向和授权；
11. HIS返回数据的写入责任方、目标表和字段映射已按接口验证；
12. 未确认内容没有通过代码默认值或模拟结果掩盖。

## 11. 当前仍需业务确认的事项

以下事项不能由开发团队自行决定：

- 健康档案和健康体检在HIS中的实际触发页面、按钮和时点；
- 修改健康档案、修改健康体检所使用的HIS对象；
- 健康档案上传对象的类型、Schema、字段、主键和读取条件；
- 健康体检两个对象的关联键及与数组字段的映射方式；
- 最新清单其他HIS对象的对象类型、Schema、字段、键、读写方向和授权；
- 每个HIS调用的返回数据由谁写入哪个HIS表，以及唯一键、字段映射和写入失败处理；
- 是否需要保存完整XML/JSON调用报文；如需保存，其用途、位置、脱敏、权限、保留期和清理方式；
- 400-003回写电子病历最终做或不做；
- 健康档案摘要在工作站中的患者选择和结果展示方式；
- 双向转诊在县医院端的实际发起、接收和结果展示流程；
- 优先顺序99和“根据实际情况”接口的实际开发顺序；
- 管理端除运行记录、基础数据运行信息以外，是否存在真实使用场景。

这些事项确认后，应把具体结论补入对应业务章节，而不是另行增加抽象状态或通用流程。
