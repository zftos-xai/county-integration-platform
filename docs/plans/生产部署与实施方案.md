# 县域医疗集成平台生产部署与实施方案

| 文档属性 | 内容 |
| --- | --- |
| 方案版本 | V1.1 |
| 编制日期 | 2026年9月17日 |
| 适用环境 | Windows Server 2012 R2、SQL Server 2012 SP4共享生产环境 |
| 适用对象 | 医院信息科、DBA、运维、平台开发、HIS及存量业务系统厂商 |
| 核心约束 | 平台与存量应用共用部署环境和SQL Server实例，平台部署不得改变存量应用的运行条件 |

## 1. 方案目标

本方案用于在不升级 Windows Server 2012 R2 和 SQL Server 2012 SP4 主版本的条件下，将县域医疗集成平台部署到已有业务系统正在运行的共享生产环境。

实施必须同时满足：

- 不中断、不重启、不改造现有业务应用。
- 不改变现有应用的 Java、.NET、ODBC、OLE DB 或 SQL Native Client 环境。
- 不改变 SQL Server 的实例名、监听端口、服务账号和全局加密策略。
- 平台使用独立的 Tomcat 10.1、Java 17、Windows 服务、端口、数据库、账号、日志和备份。
- 平台 JDBC 连接主动使用 TLS 1.2，不要求存量应用同步切换。
- 平台停止或回滚时，不触发 SQL Server 和存量应用的停止或回滚。

## 2. 实施边界

### 2.1 本次平台上线包含

- 部署独立 Java 17、Tomcat 10.1 Servlet 容器和平台 WAR。
- 部署管理端、嵌入端静态资源和获批的反向代理配置。
- 创建独立的 `county_integration` 数据库、迁移账号和运行账号。
- 执行已通过 SQL Server 2012 兼容性检查的 Flyway 主版迁移。
- 配置平台自身的 TLS 1.2 JDBC 连接和证书信任。
- 完成平台健康检查、登录引导、监控、回滚和上线观察。

### 2.2 本次平台上线不包含

以下操作会影响共享环境，必须另立“共享基础环境变更批次”，不得与平台发布合并实施：

- Windows Server 补丁安装或服务器重启。
- SQL Server GDR、CU、SP 补丁安装或 SQL Server 服务重启。
- SQL Server `ForceEncryption=1` 全局强制加密。
- 关闭 Windows Schannel TLS 1.0 或 TLS 1.1。
- 修改全局密码套件顺序、.NET 强加密开关或系统级 Java 配置。
- 替换现有应用的 JDBC、ODBC、OLE DB、SQLNCLI 驱动。
- 修改存量应用的连接串、服务账号、定时任务和运行参数。
- 修改 SQL Server 实例名、TCP 端口、服务账号或现有业务数据库。

## 3. 总体部署架构

```text
共享 Windows Server 2012 R2 生产环境
├─ 存量业务应用
│  ├─ 原有运行时、服务、端口和配置
│  └─ 原有数据库连接方式（不改变）
├─ 县域医疗集成平台
│  ├─ 独立 Java 17 目录
│  ├─ 独立 Tomcat 10.1 实例、Windows 服务和服务账号
│  ├─ 独立应用、配置、日志、临时文件目录
│  ├─ 独立 HTTP 监听端口
│  └─ JDBC TLS 1.2 主动加密连接
└─ SQL Server 2012 SP4 共享实例
   ├─ 存量业务数据库（不操作）
   └─ county_integration（独立平台数据库）
```

平台在共享 Windows Server 2012 R2 主机上使用外置 Apache Tomcat 10.1 Servlet 容器部署，不使用 Spring Boot 内嵌 Tomcat 启动生产服务。Tomcat 作为平台独立 Windows 服务运行，不与存量应用共用 Tomcat 实例、`CATALINA_HOME`、`CATALINA_BASE`、JRE、端口或 JVM。

这里的“Tomcat 容器”指 Java Servlet 容器。生产主机不新增 Docker 等操作系统级容器运行时；仓库内 `deploy/docker-compose.yml` 不作为该共享主机的生产执行方案。

当前后端工程仍按 Spring Boot 可执行 JAR 构建。进入部署实施前必须完成并验证以下 WAR 适配：

- Maven 打包类型调整为 `war`。
- 内嵌 `spring-boot-starter-tomcat` 调整为 `provided`，避免将容器实现重复打入 WAR。
- 启动类提供 `SpringBootServletInitializer` 初始化入口，同时保留本地开发所需的 `main` 方法。
- 在 Tomcat 10.1 和 Java 17 上完成启动、接口、会话、安全过滤器、Actuator、优雅停机和回滚验证。
- 生产发布物是带版本和校验和的 WAR；未完成上述适配时不得进入生产部署批次。

## 4. 隔离与资源控制

### 4.1 目录与账号

实际路径由医院运维审批，不与现有应用目录复用。建议逻辑结构：

```text
<PLATFORM_HOME>\
├─ tomcat-10.1\     平台独立 Tomcat 程序，即 CATALINA_HOME
├─ instance\        平台实例目录，即 CATALINA_BASE
│  ├─ bin\          setenv.bat 等实例启动配置
│  ├─ conf\         server.xml、context.xml 和日志配置
│  ├─ webapps\      仅部署当前 ROOT.war
│  ├─ logs\         Tomcat 和平台运行日志
│  ├─ temp\         Tomcat 临时文件
│  └─ work\         Tomcat 编译及运行缓存
├─ releases\        按版本保存的 WAR、配置快照和校验和
├─ config\          Spring 外置配置，仅服务账号和运维可读
├─ trust\           平台专用证书信任库
└─ jre-17\          平台专用 Java 17 运行时
```

平台使用独立低权限 Windows 服务账号，仅授予：

- 作为服务登录权限。
- 平台目录的必要读取和写入权限。
- 访问获批网络端点和 SQL Server 端口的权限。

不授予本地管理员、SQL Server `sysadmin` 或存量应用目录权限。

### 4.2 Tomcat 与 Java 运行时

- 使用 Tomcat 10.1.x 与 Java 17；具体补丁版本在上线前冻结并记录，不使用 Tomcat 10.0 或 Tomcat 9。
- Tomcat Windows 服务必须绑定平台 Java 17 `jvm.dll` 或 `java.exe` 的绝对路径。
- `CATALINA_HOME` 与 `CATALINA_BASE` 分离，平台实例不得扫描或部署存量应用目录。
- 独立实例仅部署一个平台应用，并命名为 `ROOT.war`，使后端接口继续保持 `/api/...` 路径；不得开启 Tomcat 自动部署和热部署。
- 外置 Tomcat 的监听端口以 `conf/server.xml` 中的 Connector 为准；`application.yml` 的 `server.port` 不作为生产端口配置。
- 删除或禁用 `docs`、`examples`、`host-manager`、`manager` 等非必需默认应用。
- 不修改系统级 `JAVA_HOME` 和 `Path`。
- 不覆盖、删除或升级存量应用的 JRE/JDK。
- 必须显式设置 JVM 最大堆，不使用“占用主机可用内存百分比”作为共享主机的生产策略。
- JVM 堆、Tomcat 工作线程、连接队列、请求体大小和临时目录限额由上线前资源基线和压测结果确定。
- Tomcat 关闭端口应禁用或限制在本机，管理接口不得对业务网段开放。

### 4.3 端口与网络

- 平台 HTTP 端口必须经端口占用检查和防火墙审批。
- Tomcat Connector 仅监听获批地址和端口；若由反向代理终止 HTTPS，应只允许代理主机访问该 Connector。
- 管理面不直接暴露到非授权网段；生产通过医院批准的 HTTPS 反向代理或网关访问。
- SQL Server 1433 或实际固定端口只向已批准的主机开放。
- 不为平台改变 SQL Server 端口或现有防火墙允许规则的含义。

### 4.4 连接池和数据库负载

- 生产必须通过 `PLATFORM_DB_POOL_MAX` 和 `PLATFORM_DB_POOL_MIN` 显式限制连接池。
- 首次上线使用保守连接数；具体数值由数据库基线、压测和业务并发量共同确定，不直接使用默认上限作为上线结论。
- 维持查询超时、分页、批量分段、并发上限和长事务监控。
- 数据同步、对账、重放和大批量任务避开 HIS 高峰和数据库备份窗口。

## 5. 数据库方案

### 5.1 逻辑隔离

```text
SQL Server 2012 SP4 共享实例
├─ 存量业务数据库       不属于平台变更范围
└─ county_integration   平台独立数据库，兼容级别110
```

禁止在 HIS 或其他业务库内创建平台表、视图、存储过程、作业或触发器。

### 5.2 账号分离

| 账号 | 用途 | 生产控制 |
| --- | --- | --- |
| `platform_migration` | Flyway 结构迁移 | 仅发布窗口启用，迁移后关闭自动迁移 |
| `platform_app` | 平台日常运行 | 只能访问 `county_integration`，不得使用 `sa` |
| `platform_his_reader` | HIS 读取获批的平台视图 | 只对逐个审批视图授予 `SELECT` |

密码通过医院批准的密钥或凭据管理方式交付，不写入版本库、发布包、启动命令行和普通工单。

### 5.3 迁移策略

1. DBA 确认目标库为 `county_integration`，并完成首次备份。
2. 发布前执行 `node tools/verify-sql-migrations.mjs`。
3. 使用 `platform_migration` 执行 Flyway，不使用 `sa`。
4. 检查 `flyway_schema_history`、对象数量、表字段注释和索引。
5. 迁移成功后设置 `PLATFORM_DB_MIGRATION_ENABLED=false`。
6. 发布后的结构变更仅允许通过新的受控迁移执行。

生产应用回滚不直接删除已执行的数据库对象。迁移必须保持向后兼容，以支持回滚到上一个应用版本。

## 6. TLS 共存方案

### 6.1 上线时状态

SQL Server 保持：

```text
ForceEncryption=0
TLS 1.2=启用
TLS 1.0/1.1=不因平台上线而关闭
```

平台 JDBC 主动请求 TLS 1.2：

```text
jdbc:sqlserver://<SQL_DNS_NAME>:<PORT>;
databaseName=county_integration;
encrypt=true;
trustServerCertificate=false;
sslProtocol=TLSv1.2;
hostNameInCertificate=<SQL_CERTIFICATE_DNS_NAME>;
trustStore=<PLATFORM_HOME>\trust\sqlserver-truststore.p12;
trustStorePassword=<SECRET>;
trustStoreType=PKCS12
```

生产应使用医院内部 CA 或医院批准 CA 签发的服务器证书。客户端通过正式 DNS 名称连接，证书 SAN 必须包含实际连接名称。

### 6.2 为什么不全局强制加密

SQL Server 2012 的 `ForceEncryption` 是实例级配置，不能按数据库、登录名或业务系统分别强制。开启后所有存量客户端都必须同时支持协商和证书信任。因此：

- 平台自身通过 JDBC 参数实现加密和证书校验。
- 存量应用保持现状，不被平台上线强制切换。
- 是否启用全局强制加密，必须在所有存量客户端盘点和验证后另行立项。

### 6.3 连接加密验证

平台连接建立后，DBA 使用只读查询确认平台会话为 `TRUE`：

```sql
SELECT
    session_info.host_name,
    session_info.program_name,
    session_info.login_name,
    connection_info.client_net_address,
    connection_info.net_transport,
    connection_info.encrypt_option
FROM sys.dm_exec_sessions AS session_info
INNER JOIN sys.dm_exec_connections AS connection_info
    ON connection_info.session_id = session_info.session_id
WHERE session_info.is_user_process = 1
  AND session_info.login_name = N'platform_app';
```

验收条件：平台会话 `encrypt_option=TRUE`，同时存量应用会话数量、加密状态和连接方式不因本次发布而改变。

## 7. 上线前准入条件

| 类别 | 准入证据 | 不满足时的处理 |
| --- | --- | --- |
| 变更边界 | 已签字的变更范围明确不含系统重启、SQL服务重启和全局TLS变更 | 不得上线 |
| 资源基线 | 已记录CPU、内存、磁盘、SQL连接、阻塞和存量应用响应时间 | 不得定义资源配额 |
| 端口 | 平台端口未占用且防火墙规则已审批 | 更换端口并重新评审 |
| Tomcat与Java | 独立 Tomcat 10.1、Java 17、服务名、端口、权限和JVM配额已确认 | 不得与存量应用共用实例或全局Java |
| WAR适配 | 工程已生成标准WAR并通过外置Tomcat 10.1验证 | 当前可执行JAR不得直接进入生产 |
| 数据库 | 独立库、独立账号、兼容级别110和备份已确认 | 不执行Flyway |
| TLS | 正式DNS、服务器证书、信任链和平台信任库已验证 | 不允许使用明文连接上线 |
| 发布包 | 版本号、校验和、构建记录和测试结果可追溯 | 拒绝手工替换不明文件 |
| 回滚 | 上一版发布包、配置备份和停止平台的步骤已演练 | 不得上线 |
| 业务验收 | 平台验收人和存量应用值守人已到位 | 改期 |

## 8. 实施批次

### 8.1 IMP-00：只读盘点与基线固化

本批次不修改任何生产配置。

1. 记录 Windows Server、SQL Server、.NET、Java 和关键驱动版本。
2. 记录所有存量服务、进程、端口、计划任务和自动启动项。
3. 连续覆盖一个完整业务周期采集 SQL Server 客户端会话。
4. 记录 CPU、内存、磁盘剩余空间与延迟、SQL 连接数、阻塞、死锁和批请求。
5. 记录存量应用的关键页面、接口、定时任务和报表基线。
6. 完成端口、目录、服务名和服务账号的冲突检查。

退出条件：基线报告已由信息科、DBA 和存量应用负责人确认。

### 8.2 IMP-01：静态资源准备

1. 创建平台服务账号和独立目录。
2. 解压平台专用 Java 17，使用绝对路径执行 `java -version`。
3. 解压已批准的 Tomcat 10.1，建立独立 `CATALINA_BASE`，清理非必需默认应用。
4. 上传已通过外置 Tomcat 验证的 `ROOT.war`、前端资源和证书信任库，核对校验和。
5. 创建外置配置、Tomcat Connector 和 JVM 参数并限制 ACL，不启动 Tomcat。
6. 确认本批次没有修改系统 `JAVA_HOME`、`Path`、Schannel 和 SQL Server 配置。

退出条件：静态文件准备完成，存量服务状态和端口无变化。

### 8.3 IMP-02：数据库初始化

1. DBA 对 `county_integration` 执行完整备份或确认为可重建空库。
2. 用迁移账号执行 Flyway，保存开始时间、结束时间、执行版本和返回码。
3. 执行 `deploy/sqlserver/03-verify-baseline.sql`。
4. 核对存量业务数据库的状态、大小、活跃连接和对象数量没有变化。
5. 将 `PLATFORM_DB_MIGRATION_ENABLED` 设为 `false`。

退出条件：平台库基线验证通过，存量库无对象和权限变更。

### 8.4 IMP-03：Tomcat 平台实例预启动

1. 通过 Tomcat Windows Service Wrapper 注册平台专用服务，服务名不得与存量服务重复。
2. 服务绑定独立 `CATALINA_HOME`、`CATALINA_BASE` 和 Java 17 绝对路径。
3. 显式配置 JVM 堆、Spring 外置配置、日志、临时目录、Tomcat 线程和连接上限。
4. 将已校验的 WAR 复制为 `webapps\ROOT.war`，先限制为本机或实施网段访问。
5. 启动平台 Tomcat 服务，检查进程、端口、应用日志、Tomcat 日志、`/actuator/health`、数据库连接和 TLS 加密状态。
6. 确认只部署一个 ROOT 应用，未启用热部署和 Tomcat 管理应用。
7. 确认平台启动没有触发 SQL Server、Windows 或存量服务重启。

退出条件：平台健康检查为 `UP`，平台会话 `encrypt_option=TRUE`，存量应用指标无异常。

### 8.5 IMP-04：功能和共存验证

1. 完成首次安全引导，删除一次性 `PLATFORM_BOOTSTRAP_SECRET` 并仅重启平台 Tomcat 服务。
2. 验证平台登录、机构、用户、角色、字典、参数、审计和已交付业务功能。
3. 验证非法账号无法访问存量数据库。
4. 运行业务验收脚本时持续观察 CPU、内存、磁盘、SQL 连接、阻塞和慢查询。
5. 由存量应用负责人复验关键登录、开单、查询、结算、接口、报表和定时任务。

退出条件：平台功能通过，存量应用业务结果和运行指标与基线一致。

### 8.6 IMP-05：正式切入和观察

1. 开放经审批的 HTTPS 入口。
2. 按机构、接口或功能开关逐步开放流量，不一次性启用全部批量任务。
3. 观察期内禁止同时执行 Windows、SQL Server、驱动和全局 TLS 变更。
4. 持续比较平台上线前后的存量应用和 SQL Server 指标。
5. 完成上线记录、问题记录、业务验收和运维交接。

退出条件：观察期结束，无存量应用回归缺陷，无平台引起的资源、锁或容量异常。

## 9. 验证清单

### 9.1 平台验证

- 平台 Tomcat Windows 服务可启动、停止和按批准策略恢复。
- 平台使用独立 Tomcat 10.1 和 Java 17，无全局 Java 环境变更。
- `CATALINA_BASE`、服务名、端口、线程池和日志与存量 Tomcat 或其他应用隔离。
- 生产运行的是已校验 `ROOT.war`，未部署 Tomcat 默认管理和示例应用。
- HTTP 端口和 HTTPS 入口符合审批范围。
- `/actuator/health` 返回 `UP`，不对外暴露健康细节。
- 平台数据库会话使用 `platform_app`。
- 平台数据库会话 `encrypt_option=TRUE`。
- 证书链和主机名校验生效，未使用 `trustServerCertificate=true`。
- Flyway 生产日常运行已关闭。
- 日志脱敏、滚动、保留和磁盘上限已验证。
- 备份、恢复和告警链路已验证。

### 9.2 存量应用无影响验证

- 存量服务没有停止或重启。
- 存量进程的 Java、.NET 和驱动加载路径没有改变。
- 存量应用连接串、DNS、端口和数据库账号没有改变。
- SQL Server `ForceEncryption` 保持原值。
- Windows TLS 1.0/1.1/1.2 全局策略没有因平台发布而改变。
- 存量业务数据库没有新增或修改对象、角色和权限。
- 存量应用关键业务回归通过。
- CPU、内存、磁盘延迟、SQL 连接数、阻塞和响应时间没有超过已批准的基线偏差。

## 10. 回滚方案

### 10.1 应用回滚触发条件

出现以下任一情况时，停止平台放量并进入回滚评估：

- 存量应用出现新增连接失败、超时或业务错误。
- SQL Server 出现由平台引起的阻塞、死锁、连接耗尽、日志或数据文件异常增长。
- 平台占用超出已批准的 CPU、内存或磁盘资源边界。
- 平台反复重启、健康检查失败或产生无法控制的重试流量。
- 发现越权访问、敏感日志泄露或证书校验被绕过。

### 10.2 应用回滚步骤

1. 关闭平台入口或功能开关，阻止新请求。
2. 等待在处理请求完成，仅停止平台 Tomcat Windows 服务。
3. 不停止 SQL Server，不重启 Windows，不操作存量应用。
4. 清理平台实例自身的 `webapps\ROOT`、`work` 和 `temp` 缓存，将 `ROOT.war` 切换到上一个已验证版本，并恢复对应配置快照。
5. 重新启动平台前，确认上一版应用与已执行数据库迁移向后兼容。
6. 对存量应用和 SQL Server 再次执行无影响检查。

平台回滚不得使用恢复整个 SQL Server 实例、回滚 Windows 系统或删除共享目录的方式处理。

## 11. 共享基础环境补丁批次

补丁批次与平台上线分离，由医院对所有受影响系统统一组织。

### 11.1 补丁分类

| 补丁类型 | 典型影响 | 实施要求 |
| --- | --- | --- |
| Windows Server 补丁 | 需整机重启，影响所有应用 | 所有业务负责人共同确认维护窗口 |
| SQL Server GDR | 需 SQL Server 服务重启，中断全部数据库连接 | 全库备份、回归和回滚决策点必须齐备 |
| .NET/Schannel 补丁 | 可能改变老应用TLS协商 | 覆盖所有.NET、ODBC、OLE DB和系统服务回归 |
| 客户端驱动 | 影响单个应用的连接行为 | 按业务系统单独分批，不全机覆盖 |
| SQL Server 证书换发 | 需 SQL Server 服务重启 | 先向客户端分发新CA链，再在维护窗口切换 |

### 11.2 SQL Server 2012 补丁评估

已知 `11.0.7507.2` 为 SQL Server 2012 SP4 GDR KB4583465。正式补丁评估需核对微软版本列表、当前组件、版本分支、医院补丁制度和授权条件。如评估更新的 SP4 GDR，必须在生产同版本克隆环境完成所有共享应用回归，不以“平台连接正常”代替整体验收。

## 12. 运维监控与证书轮换

### 12.1 必须监控的指标

- 平台进程、健康检查、重启次数和线程数。
- JVM 堆、GC、Tomcat 线程池、Connector 连接、CPU、磁盘和日志增长。
- HikariCP 活跃、空闲、等待和超时连接。
- SQL Server 平台登录的连接数、长事务、阻塞、死锁和慢查询。
- `county_integration` 数据和日志文件增长、备份、完整性检查和恢复演练。
- TLS 证书到期时间、信任链和 Schannel/SQL ERRORLOG 协商错误。
- 存量业务应用的已批准关键指标，用于判定平台是否造成影响。

### 12.2 证书轮换

1. 至少在到期前的医院规定周期内触发告警和换发流程。
2. 新证书 SAN 覆盖当前全部获批 DNS 名称。
3. 先将新 CA 链纳入平台信任库，保留旧链完成重叠验证。
4. SQL Server 证书绑定和服务重启在共享维护窗口实施。
5. 验证新证书后再从平台信任库移除旧链。

## 14. 上线结论模板

上线结论必须分别回答：

1. 平台是否通过功能、权限、TLS、性能和回滚验证。
2. 存量应用是否通过无影响回归。
3. 共享环境是否存在新增资源、连接、锁、容量或稳定性风险。
4. 是否存在需要另立共享基础环境变更批次的补丁、证书或TLS工作。

只有平台验证和存量应用无影响验证均通过，才能宣布本批次上线完成。
